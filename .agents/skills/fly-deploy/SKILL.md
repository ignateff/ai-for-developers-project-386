Деплой Dockerfile-приложения на Fly.io Machines. Полный справочник fly.toml и лестница отладки: [reference/fly-io.md](reference/fly-io.md) — открывай его, когда шаг ссылается на детали конфигурации или когда деплой упал.

## Гардрейлы

- `fly auth login` — шаг пользователя: если браузер не открылся, покажи ссылку из вывода и жди подтверждения. Не пытайся логиниться за пользователя.
- Значения токенов и секретов никогда не печатай и не сохраняй в файлы. Для headless-прогонов используй `FLY_API_TOKEN` из окружения; `fly auth token` для автоматизации не используй (короткоживущий и всемогущий).
- Деструктивные команды (`fly machine destroy`, `fly volumes delete`, `fly secrets unset`, `fly apps destroy`) — только после явного запроса пользователя.

## Шаги

### 1. Предусловия

- Перед подготовкой сборки для деплоя выполни Git-gate из [AGENTS.md → Deployment](../../../AGENTS.md#deployment). Для read-only диагностики live-сервиса смена ветки не нужна. Порядок gate:
  1. Проверь `git status --porcelain=v1 --untracked-files=all` и `git worktree list`. При непустом status остановись. Если `main` занят другим worktree, используй его только после проверки принадлежности и доступности; иначе сообщи блокер, не переключай чужой checkout принудительно.
  2. Выполни `git fetch origin`, затем в доступном checkout — `git switch main` и `git merge --ff-only origin/main`. Каждая команда должна завершиться успешно; при ошибке остановись без автоматических stash/reset/clean.
  3. `git branch --show-current` должен вернуть `main`; `git rev-parse HEAD refs/heads/main refs/remotes/origin/main` — три одинаковых полных SHA; повторный `git status --porcelain=v1 --untracked-files=all` — пустой вывод. Одного успешного `--ff-only` недостаточно: локальный `main` может быть впереди `origin/main`.
  4. Зафиксируй полный SHA как `SOURCE_REVISION` в данных текущего деплоя. Временный build context допустим как неизменяемый снимок этого коммита, а не самостоятельный источник из другой ветки; Git-gate повторяют в исходном checkout. Игнорируемые файлы по-прежнему проверяются отдельно в шаге 5.
- Найди исполняемый CLI через `command -v fly`, затем проверь `~/.fly/bin/fly`. Сохрани найденный абсолютный путь и используй его во **всех** вызовах ниже, где написано `fly`; отдельные shell-вызовы не сохраняют переменные предыдущего. Нет CLI — `curl -L https://fly.io/install.sh | sh`, затем повтори поиск.
- Проверь auth найденным CLI: `fly auth whoami`. Ошибка авторизации — переходи к `fly auth login` (см. гардрейлы); транспортную ошибку диагностируй по шагу 7, а не считай потерей авторизации.

Готово, когда для деплоя пройден Git-gate и записан `SOURCE_REVISION`, известен исполняемый путь и `whoami` печатает identity.

### 2. Готовность приложения

- В корне проекта есть `Dockerfile`; приложение стартует автоматически при запуске контейнера, слушает `0.0.0.0:$PORT` (не `127.0.0.1`), есть health-эндпоинт с ответом 200 без редиректа.
- До любой сборки проверь build context по шагу 5. Если доступен Docker: собери образ с тем же безопасным контекстом и прогони контейнер с переопределённым `PORT`.
- Если образ велик или push медленный, измерь размер и слои; оптимизацию runtime и Docker-проверки планируй по [разделу об образе](reference/fly-io.md#размер-образа-и-docker-проверки), отдельно от восстановления текущего деплоя.

Готово, когда образ собирается, а контейнер отвечает на health-эндпоинте по порту из `PORT`.

### 3. Первый запуск (fly.toml ещё нет)

Из корня проекта, неинтерактивно:

```sh
fly launch --name <repo-name>-<suffix> --region <r> --no-deploy --yes \
  --no-db --no-redis --no-object-storage --dockerfile Dockerfile
```

- Имя глобально уникально: имя репозитория + короткий суффикс; регион — `fly platform regions`.
- SQLite-приложение (один писатель): добавь `--ha=false` — иначе две Machines ⇒ два volume ⇒ split-brain.
- Существующий Dockerfile проекта не заменять и не перегенерировать.
- Нет Dockerfile и не нужен свой — позволь launch сгенерировать, потом правь.

Готово, когда создан `fly.toml` и приложение видно в `fly apps list`.

### 4. Настройка fly.toml

Проверь/выставь (схема и оговорки — в reference):

- `[http_service] internal_port` = порт приложения; `force_https = true`; autostop/autostart по дефолту launch (scale-to-zero).
- `[[http_service.checks]]` на health-эндпоинт; помни: checks не следуют редиректам.
- `[env]`: `PORT` (должен совпадать с `internal_port`) и прочие несекретные переменные; секреты — только `fly secrets set` (каждый set перезапускает Machines — группируй).
- `[[vm]] size = "shared-cpu-1x"` с явной `memory`.
- SQLite: `fly volumes create data -r <primary_region> -s 1`, затем `[mounts] source = "data", destination = "/data"` и `[env] DATABASE_PATH = "/data/<file>.sqlite"`. Одна Machine на volume, всегда. Снапшоты volume — не бэкапы; скажи это пользователю.

Проверка: `fly config validate` зелёный.

### 5. Деплой

- Найди существующую проектную deploy-задачу и проверь её реализацию; используй её, если она выполняет этот процесс безопасно. Если задачи нет, выполняй CLI-шаги ниже; повторяемую подготовку автоматизируй только в согласованной задаче по [требованиям к deploy-команде](reference/fly-io.md#проектная-deploy-команда).
- Проверь `git status --short`, `Dockerfile`, `.dockerignore` и фактический build context, включая игнорируемые и неотслеживаемые файлы: `COPY . .` может включить локальные данные. Исключи ненужное без изменения пользовательских файлов; для временного ignore-файла сохрани правила `.dockerignore` и проверь поддержку `--ignorefile` в `fly deploy --help`. При сомнении о содержимом или допустимости отправки спроси пользователя.
- Для существующего приложения зафиксируй исходные release, image и Machines. Передай `SOURCE_REVISION` (или его однозначное сокращение) при сборке frontend, а не только в runtime env; сохрани соответствие полного SHA, проверенного контекста и image digest. Dirty/unknown-сборки пригодны для отдельных локальных экспериментов, но не проходят проектный gate деплоя.
- Непосредственно перед registry push и перед запуском `fly deploy` повтори Git-gate шага 1, включая свежий fetch. Сравни новый полный SHA с `SOURCE_REVISION`: если он изменился, прежний артефакт больше не подходит для обычного деплоя — подготовь новый контекст, пересобери и повтори Docker-проверку. Для готового образа `--image` требуется установленное соответствие digest этому SHA; один тег или строка версии не доказывают происхождение образа.
- Настрой **внешний тайм-аут инструмента** на всю сборку, push и rollout до запуска команды: длительная операция с уведомлением/ожиданием завершения либо достаточный явный бюджет. Двухминутный лимит не подходит как автоматический выбор. Параметры OpenCode и отличие от тайм-аутов Fly: [жизненный цикл команды](reference/fly-io.md#тайм-ауты-и-жизненный-цикл-команды).
- `fly deploy` из корня проекта. Стратегия — дефолтный `rolling`; с примонтированным volume canary/bluegreen запрещены платформой. Медленный старт — `--wait-timeout`, а не повторные прогоны.

Готово, когда команда завершилась кодом 0 и известен опубликованный image reference/digest. Локальная сборка или начавшийся push ещё не означают деплой; при прерывании переходи к шагу 7.

### 6. Проверка

- Сверь релиз, образ и состояние всех целевых Machines; при autostop `stopped` допустим.
- `curl -fsS https://<app>.fly.dev/<health>` → 200; проверь `fly checks list` и `fly logs -n` после запуска. `started` сам по себе не означает, что сервис здоров.
- Проверь изменённую функцию на публичном приложении. Для frontend-версии открой свежую браузерную сессию, сопоставь строку в Console с ожидаемой сборкой и проверь JS-ошибки; здоровый старый backend тоже может отвечать 200.

Готово, когда ожидаемый образ развёрнут на целевых Machines, публичный health-эндпоинт отвечает 200, проверки работающих Machines и изменённой функции проходят; остановленные из-за autostop оцени отдельно.

### 7. Если сломалось

Открой [лестницу отладки](reference/fly-io.md#диагностика-и-восстановление) и выбери ветку по стадии ошибки: Fly API, builder, сборка, **registry push** или запуск приложения. EOF/timeout не доказывает, что операция не выполнена. После возможной мутации сверь фактическое состояние и побочные эффекты release command до повторного деплоя; если состояние неизвестно, остановись и сообщи пользователю. Перед повтором после ошибки, ожидания или паузы заново выполни шаг 1 и сравни SHA с артефактом по шагу 5; фоновый монитор тоже обязан выполнять этот gate. Не запускай деплои параллельно. Для отката действует отдельное исключение из AGENTS.md: явное разрешение пользователя и проверки происхождения образа, совместимости данных и конфигурации; откат не отменяет миграции БД.

### 8. Следующие изменения

Повторяй Git-gate шага 1 и шаги 5–6 через проверенную проектную задачу или `fly deploy`. Machine и volume для обычного обновления пересоздавать не нужно.

## Запасной путь без проекта

Только если пользователь просит поднять готовый публичный образ без исходников: `fly apps create --generate-name`, `fly machine run <image> --app <name> --port ...`, затем обязательно `fly ips allocate-v4 --shared` и `fly ips allocate-v6` (у `machine run` нет публичных IP — в отличие от launch/deploy, где Anycast-IP выделяются автоматически). Во всех остальных случаях — путь через `fly launch`.
