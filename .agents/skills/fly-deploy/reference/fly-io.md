# Справочник Fly.io для скилла fly-deploy

Источник фактов: docs.fly.io + `fly --help` (v0.5.1), собрано в исследовании 2026-11-02. Документация и CLI могут расходиться — при сомнениях доверяй локальному `fly <cmd> --help`.

## fly.toml (Machines / Apps V2)

```toml
app = "my-app"                    # первый ключ; даёт hostname <app>.fly.dev
primary_region = "fra"            # где fly deploy создаёт новые Machines

[build]
dockerfile = "Dockerfile"         # путь не меняет build context (он всегда корень проекта)

[env]
PORT = "8080"                     # только строки; имена не с FLY_; секреты переопределяют
DATABASE_PATH = "/data/app.sqlite"

[http_service]
internal_port = 8080              # должен совпадать с портом приложения
force_https = true                # 301 HTTP→HTTPS; только на http-обработчиках
auto_stop_machines = "stop"       # "off" | "stop" | "suspend"
auto_start_machines = true        # включать/выключать парой с auto_stop
min_machines_running = 0          # только primary-регион

  [[http_service.checks]]
  grace_period = "10s"            # время на старт приложения
  interval = "30s"
  method = "GET"
  timeout = "5s"
  path = "/api/health"            # эндпоинт с 200 без редиректов — checks за редиректами НЕ следуют

[[vm]]
size = "shared-cpu-1x"            # пресеты: fly platform vm-sizes
memory = "512mb"

[mounts]
source = "data"                   # volume с этим именем должен существовать в регионе
destination = "/data"             # не "/"
snapshot_retention = 5            # дни, 1–60

[deploy]
strategy = "rolling"              # с volume только rolling|immediate; canary/bluegreen запрещены
```

Проверка: `fly config validate`.

## Ключевые факты

- **Сеть.** `[http_service]` даёт Anycast IPv6 + shared IPv4 автоматически на первом `fly deploy`; `fly ips allocate-*` нужен только для пути `fly machine run`. Fly Proxy слушает 80/443 и шлёт на `internal_port`; TLS терминируется на границе, к Machine идёт plaintext; приложение обязано слушать `0.0.0.0`. Прокси добавляет `X-Forwarded-Proto`, `Fly-Client-IP` и др.
- **Machines.** Холодный старт из `stopped` ≈ 2 с+; `suspended` быстрее, но со сдвигом часов (ломает JWT/cron/TTL/TLS сразу после resume — для таких приложений `stop`, не `suspend`). Autostop не создаёт/не удаляет Machines. Застрявшая: >5 мин в `starting`/`stopping`/`destroying`, >10 мин в `updating`.
- **Volumes.** Один volume ↔ одна Machine; локальный NVMe, привязан к региону, без репликации. Ежедневные снапшоты (5 дней дефолт) — не бэкап-стратегия. Volumes только растут, не уменьшаются. Недоступны при сборке и в `release_command`. Тарифицируются за полный размер даже на остановленной Machine. Создание: `fly volumes create <name> -r <region> -s 1`; восстановление: `fly volumes create <name> --snapshot-id <id> -r <region>`.
- **Секреты.** `fly secrets set NAME=VALUE` (или stdin) — каждый вызов перезапускает Machines; `--stage` откладывает до следующего деплоя. `fly secrets list` показывает имена и дайджесты, значения нечитаемы. Runtime secrets автоматически в сборку не передаются; для build secrets используй `--build-secret`, а `[build.args]` — только для несекретных значений.
- **Деплой.** Образ по приоритету: `--image` → `[build]` → `--dockerfile` → `./Dockerfile`. Дымовые проверки ~10 с после старта Machine; повторные падения останавливают деплой. Отката-команды нет: `fly releases --image` + `fly deploy --image registry.fly.io/<app>:<tag>`; `--image-label` для читаемых меток.
- **Наблюдение.** `fly status [--all|--watch]`, `fly machines list`, `fly logs [-n|-m <machine>|-r <region>]`, `fly checks list`, `fly ssh console [-C "cmd"]`.

## Тайм-ауты и жизненный цикл команды

Различай три независимых бюджета:

| Бюджет | Что ограничивает |
| --- | --- |
| Тайм-аут shell-инструмента / CI job | Всю команду: сборку, загрузку слоёв, release command и rollout. Его истечение может убить `fly deploy` во время исправной публикации. |
| `fly deploy --wait-timeout` | Ожидание перехода отдельной Machine в готовое/здоровое состояние, не registry push. |
| `fly deploy --release-command-timeout` | Выполнение release command, не всю команду агента. |

До запуска выбери режим по возможностям инструмента:

- **OpenCode shell с уведомлением о завершении:** `background: true, timeout: 0` убирает внешний лимит для этой длительной операции. Сохрани job ID и дождись уведомления с итоговым кодом; это не `fly deploy --detach`.
- **Без уведомлений:** используй поддерживаемое блокирующее ожидание и явный бюджет на весь процесс, например 20–30 минут с поправкой на размер образа и сеть. Если продолжить ожидание нельзя, сообщи, что операция ещё выполняется, вместо объявления успеха или запуска второй команды.

Читай лог для диагностики конкретной стадии; не заменяй уведомление циклом sleep/poll. При остановке или тайм-ауте сохрани последний подтверждённый этап и выполни сверку состояния из раздела восстановления. Увеличение бюджета устраняет преждевременное прерывание, но само по себе не исправляет EOF, авторизацию или зависший процесс.

## Артефакт и стадии деплоя

| Стадия | Проверяемый результат |
| --- | --- |
| Build | Образ собран и локально проверен; известны platform и local image ID. |
| Registry push | Публикация манифеста завершена; известны remote image reference и registry digest. Сообщения `Pushed` для отдельных слоёв недостаточны. |
| Rollout | Целевые Machines используют ожидаемый registry digest/release; их состояние и checks проверены. |
| Публичная проверка | Health отвечает 200 и наблюдается изменённая функция приложения. |

Local image ID и registry manifest digest — разные идентификаторы: сравнивай `image_ref.digest` машины с digest опубликованного манифеста, а не с local image ID. Тег может быть перезаписан; для восстановления зафиксируй digest.

Сохрани безопасный build context и build arguments до завершения проверки. Привяжи контекст и registry digest к полному `SOURCE_REVISION`, полученному после [Git-gate шага 1](../SKILL.md#1-предусловия). Перед публикацией, запуском деплоя и каждым повтором после ошибки/паузы заново выполни gate: артефакт должен соответствовать текущему проверенному коммиту. Изменение исходников, платформы или метаданных означает новую сборку с новой проверкой, а не продолжение прежней публикации. Сохранённый snapshot или готовый digest не разрешает выкатить устаревший коммит. Подготовка временного контекста сохраняет проектные ignore-правила и исключает локальные базы, секреты и служебные настройки. Исключение для явно разрешённого отката задаёт [AGENTS.md → Deployment](../../../../AGENTS.md#deployment).

## Диагностика и восстановление

Зафиксируй время, версию `fly version`, этап, endpoint и ошибку без секретов; проверь [статус Fly.io](https://status.flyio.net/) и соответствующую ветку. EOF или timeout не устанавливает первопричину и не доказывает, что сервер не выполнил запрос.

1. **Fly API недоступен:** проверь `fly status --all`, доступность API и статус сервиса; безопасное чтение можно повторить ограниченное число раз с задержкой. Различай сетевой EOF и полученный HTTP-ответ. `fly doctor` помогает с диагностикой, но ошибка агента не доказывает причину EOF. Смена builder не обходит Machines API.
2. **Depot недоступен до сборки:** после сверки состояния попробуй `fly deploy --local-only` при работающем Docker или `--depot=false` для legacy remote builder ([Fly troubleshooting](https://docs.fly.io/getting-started/troubleshooting/#build-hangs-waiting-for-depot-builder)). Локальной сборке нужны ресурсы, сеть для зависимостей и registry; проверь совместимость архитектуры образа и нативных зависимостей с целевой Machine. Удалённый builder может требовать ресурсов и не обязан быть доступен. Оба варианта зависят от registry и Machines API. Используй тот же проверенный build context.
3. **Ошибка сборки:** изучи вывод сборки и `fly config validate`; при необходимости воспроизведи локально с тем же контекстом и Dockerfile. `--no-cache` не исправляет сетевой handshake.
4. **Registry push:** установи, завершена ли публикация манифеста по [критериям стадий](#артефакт-и-стадии-деплоя), и что остановило загрузку: внешний тайм-аут, транспортная ошибка или HTTP-ответ. Для медленного push проверь [размер и слои](#размер-образа-и-docker-проверки). `no basic auth credentials` от отдельного Docker-клиента не доказывает, что авторизация `fly deploy` тоже не работает. Обычную registry-аутентификацию выполняй без печати токенов и без отключения TLS. После сверки состояния и повторного Git-gate публикацию того же образа можно продолжить, только если его `SOURCE_REVISION` остался актуален; уже загруженные слои могут использоваться повторно, но это не гарантия завершения push. Если манифест уже опубликован, доступен и соответствует проверенному коммиту, используй `fly deploy --image <registry>/<repository>@sha256:<digest>` вместо новой сборки. Этот вызов всё равно меняет production и требует проверки состояния, Git-gate и разрешения на деплой. Для устаревшего образа требуется отдельно разрешённый откат, а не обычный retry.
5. **Обновление или запуск:** проверь `fly status --all`, `fly machines list`, `fly releases --image`, `fly checks list`, `fly logs -n` и `fly machine status <id>`. Сопоставь образ и события каждой целевой Machine; появление релиза не доказывает завершение rollout. При autostop `stopped` допустим, а `started` не гарантирует здоровье.

**Неизвестный исход мутации:** до повтора сверь состояние релизов и всех Machines, конфигурацию и возможные побочные эффекты `release_command` (включая миграции). Если чтение API недоступно или состояние нельзя установить, остановись и сообщи пользователю. Не выполняй параллельные деплои и не предполагай идемпотентность release command. Если повтор нужен и безопасен, заново выполни Git-gate, выбери соответствующий ему артефакт, выполняй деплой последовательно и снова проверь результат. Откат — отдельное изменение production по исключению AGENTS.md: получи явное разрешение пользователя на конкретный прежний образ, проверь его происхождение, совместимость данных и конфигурации и доступность digest. Старый образ не откатывает миграции, конфигурацию или секреты. Не пересоздавай Machine или volume для устранения EOF.

502 = приложение упало или слушает не тот адрес/порт; 503 = нет здоровых Machines; «not listening on the expected address» = привязка к 127.0.0.1 или несовпадение с `internal_port`. Machine глохнет сразу после старта = процесс завершается (нет CMD / ошибка на старте) — проверить `docker run` локально. Лимит образа 8 ГБ rootfs. Registry 401 при пуше → перелогин или https://status.flyio.net.

## Размер образа и Docker-проверки

Когда push медленный или образ заметно вырос, измерь, а не меняй Dockerfile наугад:

```sh
docker image inspect <image> --format '{{.Size}} {{.Os}}/{{.Architecture}}'
docker history <image> --format '{{.Size}}\t{{.CreatedBy}}'
```

Историю показывай только для проверенного Dockerfile без секретов в build arguments/командах. Размер локального образа — не размер сжатой сетевой передачи. Большой слой зависимостей объясняет объём артефакта, но не доказывает причину EOF или сбой Fly.io.

Оптимизацию оформляй отдельной согласованной задачей, сохраняя проверенный образ для текущего восстановления:

- Multi-stage build: инструменты сборки и dev dependencies остаются в builder; runtime содержит production dependencies, собранный API/frontend и нужные миграции/ресурсы.
- Проверь платформу и нативные зависимости (для этого проекта — `better-sqlite3`); slim runtime должен содержать необходимые системные библиотеки.
- Добавь автоматический Docker build/smoke-check в существующую систему проверок проекта и CI: нестандартный `PORT`, изолированная временная/in-memory БД без production volume, health и загрузка frontend-артефакта. Чисти только созданные проверкой ресурсы. Проверка не требует Fly credentials и не выполняет деплой.
- Если нужен лимит размера, согласуй порог и проверяй его автоматически. Обычные lint/typecheck/test/build приложения не доказывают корректность контейнера; сначала прочитай реальные CI/mise-задачи, чтобы расширить существующий guardrail.

Готово, когда оптимизированный runtime проходит Docker-проверки на целевой платформе, измерен новый размер и нужные ресурсы не потеряны; уменьшения числа мегабайт недостаточно.

## Проектная deploy-команда

Используй существующую команду только после чтения её реализации. Имя вроде `mise run deploy:fly` — предложение для этого репозитория, **не утверждение, что задача уже существует**. Создание команды и изменение CI требуют отдельной согласованной задачи; документация скилла не заменяет их реализацию.

Для повторяемой автоматизации нужны:

1. Найденный исполняемый путь CLI (включая fallback вне PATH) и однозначные app/config/context; аргументы передаются без shell-конкатенации секретов.
2. Проверенный allowlist/ignore-контекст без локальных данных и секретов, снимок/проверка его неизменности между smoke-test и публикацией, явная целевая platform.
3. Git-gate шага 1 до сборки, перед публикацией/деплоем и при каждом retry/resume; соответствие артефакта текущему `SOURCE_REVISION`, блокировка dirty/missing Git metadata и устаревших образов. Build-time release/revision; frontend не получает revision задним числом из runtime env. Исключение отката — только по правилам AGENTS.md.
4. Длительный запуск по [правилам тайм-аутов](#тайм-ауты-и-жизненный-цикл-команды), сохранение exit status и диагностики, последовательные операции без автоматического повтора мутаций с неизвестным исходом.
5. Сверка исходного состояния, опубликованного digest, всех целевых Machines, checks, публичного health и изменённой функции; неполная проверка возвращает незавершённый результат, а не успех.
6. Тесты с подставным CLI/HTTP, без реальных учётных данных: Git-gate (другая ветка, dirty/untracked, локальный main впереди или позади origin/main, divergence, ошибка fetch, main в другом worktree, продвижение origin/main во время сборки/ожидания), fallback-путь CLI, исключение секретов/БД из контекста, build arguments, изменение контекста после проверки, ошибка/прерывание push, неизвестный исход rollout без слепого повтора, propagation exit code и успешная проверка ожидаемого digest. Это требования к будущей автоматизации, не утверждение о существующих тестах.

Для этого проекта actionable script имеет одноимённую mise-задачу; тесты подготовки входят в существующий test/CI. Секреты не попадают в сохранённые аргументы, тестовые fixtures или логи. В скилле остаётся ссылка на задачу и её ограничения, а детали подготовки — в коде и тестах.

## Флаги CLI

Доступные флаги и значения по умолчанию проверяй в локальном `fly <command> --help`: версии CLI и документации могут различаться. Не сохраняй токены и секреты в диагностических логах.

## Непроверенное

- Точный текст интерактивных промптов `fly launch` для пути с чистым Dockerfile (флаги проверены, текст — нет, чтобы не мутировать состояние).
- Открывает ли launch веб-страницу «tweak settings» для Dockerfile-сканера в v0.5.1.
- Расхождение: документация пишет `fly version update`, в v0.5.1 это `fly version upgrade`.

У Fly.io есть официальные agent-скиллы (`fly setup agent`, `fly skills install`) и MCP-сервер — если пользователь их установил, они могут дублировать этот скилл.
