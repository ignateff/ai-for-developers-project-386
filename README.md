# Календарь звонков


[![hexlet-check](https://github.com/ignateff/ai-for-developers-project-386/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/ignateff/ai-for-developers-project-386/actions)

## Обзор проекта

«Календарь звонков» — учебный full-stack проект Хекслета, который разрабатывается совместно с ИИ. Цель проекта — создать сервис, где владелец публикует типы встреч, а гости без регистрации выбирают свободное время и записываются на звонок.

Владелец может управлять типами встреч и просматривать предстоящие записи, а гость — выбирать свободное время и бронировать встречу.

### Устройство проекта

- `apps/web/` — frontend на React, Vite и Mantine.
- `apps/api/` — backend на Fastify и дымовой тест.
- `contract/` — исходный контракт API на TypeSpec и настройки генератора SDK.
- `generated/` — OpenAPI-спецификация и клиентский SDK, созданные из контракта.
- `mise.toml`, `hk.pkl` — версии инструментов, команды разработки и Git-хуки.
- `docs/adr/` — архитектурные решения проекта.

## Сценарий записи на звонок

1. Владелец создаёт тип встречи: указывает название, описание и длительность. Тип становится доступен гостям.
2. Гость без регистрации выбирает тип встречи и открывает календарь на ближайшие 14 календарных дней.
3. Гость выбирает дату и свободное время, заполняет необходимые данные для записи и подтверждает её.
4. Приложение сохраняет встречу и показывает гостю подтверждение. Занятый интервал больше недоступен для бронирования, в том числе для других типов встреч.
5. Владелец открывает список предстоящих встреч и видит новую запись вместе с записями других типов.

Один владелец задан заранее. Авторизации, личных кабинетов и интеграций с внешними календарями нет. Длительность слота и шаг между началами слотов равны длительности выбранного типа встречи. Встречи не могут пересекаться даже частично; следующая встреча может начинаться сразу после окончания предыдущей. Это правило действует и при одновременных запросах на запись.

Контракт API описывается в TypeSpec, из него генерируется OpenAPI-спецификация, а из неё — клиентский SDK для фронтенда. Приложение должно собираться в Docker-образ и запускаться в контейнере.

## Развёрнутое приложение и данные

Приложение: https://call-calendar-k7f2.fly.dev/ (доступность зависит от состояния Fly.io и его биллинга).

На Fly.io SQLite хранится в подключённом постоянном томе `/data`: при обычном перезапуске машины и повторном деплое данные сохраняются, пока сохраняется этот том. Удаление или повреждение тома может привести к потере данных; снимки тома не заменяют проверенные резервные копии. При локальном запуске Docker без подключённого тома данные остаются только в файловой системе контейнера и теряются при его удалении. Демо на Render Free использует временное хранилище: данные теряются при остановке, перезапуске или деплое.

## MCP для OpenCode

Безопасный пример конфигурации Render MCP находится в `opencode.example.json`. При необходимости объедините его с существующим `opencode.json` или скопируйте в `opencode.json`, если своего файла ещё нет. Создайте API-ключ в настройках Render и передайте его процессу OpenCode через переменную окружения `RENDER_API_KEY`; не сохраняйте ключ в репозитории и не отправляйте его в чат. MCP получает доступ к ресурсам аккаунта, включая изменение сервисов. Подробнее: [инструкция по Render](docs/deploy/render.md).

## Установка

Установите [mise](https://mise.jdx.dev/getting-started.html) и убедитесь, что команда `mise` доступна в `PATH`. Затем:

```bash
git clone https://github.com/ignateff/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise trust
mise install
mise run install
mise run install-hooks
```

`mise run install` устанавливает зависимости. `mise run install-hooks` отдельно устанавливает Git-хуки, общие для worktree репозитория; при подготовке дополнительного worktree повторно устанавливать их не требуется.

## Использование

```bash
mise run dev         # запустить API и frontend и вывести адрес
mise daemons ls      # проверить состояние
mise daemons stop    # остановить
mise run check       # все проверки и сборка
mise run lint        # линтер
mise run test        # дымовой тест
```

По умолчанию используются порты 5173 для frontend и 3000 для API. Если порт занят, выбирается следующий свободный; фактический адрес frontend выводится после запуска. Разные папки проекта запускают независимые серверы и используют отдельные локальные базы данных. `mise daemons stop` останавливает только серверы текущей папки.

Для явного выбора портов задайте `PORT` (API) и/или `WEB_PORT` (frontend), например `PORT=3100 WEB_PORT=5180 mise run dev`. Занятый явно заданный порт вызывает ошибку. `API_PROXY_TARGET` позволяет явно задать адрес API для прокси frontend. Для запуска каждого сервера на переднем плане используйте `mise run dev-api` и `mise run dev-web` в разных терминалах.

Настройка GitHub App и порядок выпуска описаны в [инструкции по релизам](docs/release.md).

### Проверка версии фронтенда

После перезагрузки страницы откройте Console в инструментах разработчика браузера
и включите уровень Info. Приложение один раз выводит `Calendar v0.3.1 (a1b2c3d)`:
версия берётся из `version.txt`, хеш — из коммита сборки. В режиме разработки
добавляется `[dev]`. Переходы внутри приложения не повторяют сообщение.

Для Docker используйте `mise run build:docker`: команда автоматически передаёт
хеш текущего коммита и создаёт образ `call-calendar`. При самостоятельной сборке
можно передать `--build-arg APP_REVISION="$(git rev-parse HEAD)"`; этот же аргумент
поддерживает `fly deploy`. Git-история в образ не включается. Если хеш недоступен
или не передан, вместо него будет `unknown` — сборка при этом продолжится.

Это версия **загруженного фронтенда**, не подтверждение версии бэкенда или
успешного деплоя всех компонентов. Сравнивайте её с ожидаемым коммитом в GitHub;
если браузер сохранил старую страницу, перезагрузите её с отключённым кешем.
Повторная сборка одного коммита показывает ту же версию; незакоммиченные локальные
изменения не меняют хеш HEAD. Отдельных запросов для проверки версии нет.

### Подготовка образа для деплоя

`mise run deploy:prepare` (или `pnpm run deploy:prepare`) явно собирает локальный
образ `linux/amd64`; команда ничего не публикует и не запускает на Fly. Запускайте
её из корня чистого checkout на `main`: она делает свежий `fetch origin`,
`merge --ff-only origin/main` и требует равенства всех трёх ревизий. Нужны доступ
к origin и работающий Docker. Контекст собирается только из разрешённых файлов
проверенного Git-коммита; локальные файлы и Git-история в него не копируются.

При успехе команда выводит путь к приватному временному `provenance.json`: там
записаны полный исходный SHA, манифест контекста, платформа и проверенный local
image ID. `registryDigest: null` означает, что публикации не было; local image ID
не является registry digest. Перед любой последующей публикацией и rollout
обязательны повторный Git-gate, проверка происхождения артефакта и остальные
правила [fly-deploy](.agents/skills/fly-deploy/SKILL.md). Этот файл сам по себе
не разрешает публиковать устаревший образ.
