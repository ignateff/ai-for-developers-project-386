# Организация бэкенда по предметным областям

Код Fastify-сервера группируем в `apps/api/src/` по предметным областям, а не в общие папки маршрутов, сервисов и моделей. Так связанные операции, правила и тесты находятся рядом, а `app.ts` не превращается в файл со всеми сценариями. Текущие области — `meeting-types`, `bookings`, `availability` и `events`; новый код помещаем в существующую область по его ответственности или создаём новую, если он относится к самостоятельной области.

Внутри области размещаем маршруты Fastify в `routes.ts`, а операции, предметные правила, запросы к базе и транзакции — в сервисе или других принадлежащих области модулях. Маршрут принимает и проверяет HTTP-данные, вызывает операцию и преобразует её результат в HTTP-ответ; сервис возвращает результат операции, оставляя выбор HTTP-статуса маршруту. Небольшие вспомогательные функции и валидация могут жить в отдельных файлах области. Например, проверка формата и диапазона параметра даты сейчас находится в маршруте доступности. Не создаём обязательные слои или репозитории для каждого простого запроса: выделяем их, когда они упрощают конкретную область.

`app.ts` собирает приложение, общие обработчики и регистрирует маршруты; `server.ts` запускает сервер. Общее подключение к базе и схема Drizzle находятся в `database/`, миграции — в `apps/api/drizzle/`. Код, нужный нескольким областям, размещаем там, где понятна его ответственность: области могут использовать подходящие функции других областей, а инфраструктура остаётся общей. Не переносим код в общую папку только ради повторного использования названия слоя.

Тесты области размещаем рядом с её кодом. Общие проверки приложения и HTTP-контракта могут оставаться в корне `src/`. Новые операции сначала описываем в TypeSpec и покрываем контрактными тестами для каждого сценария ответа согласно `AGENTS.md` и `docs/agents/testing.md`. Это решение не меняет контракт API и правило атомарной транзакции записи из ADR 0001.
