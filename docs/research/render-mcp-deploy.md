# Деплой проекта через Render MCP

Дата проверки источников: 2026-11-02. Исследование по официальной документации Render, исходному репозиторию Render MCP и документации OpenCode V2. Цены и схемы могут измениться. Связанное исследование: [Fly.io](fly-io-cli-deploy.md).

Последующая попытка: Render MCP подключён по API-ключу; живая схема `create_web_service` принимала `free`, но запрос с этим тарифом вернул HTTP 402 с требованием платёжных данных. При попытке через Dashboard пользователь также увидел требование карты. Причина не установлена; успешный деплой не подтверждён. Документация Render [описывает работу без платёжного метода](https://render.com/docs/free), поэтому нельзя обобщать это требование на все аккаунты.

## Вывод

Hosted MCP `https://mcp.render.com/mcp` позволяет агенту создавать Git-backed Docker web service, запускать deploy и читать статус и логи, но **не покрывает полноценную настройку SQLite-диска**: нужен Dashboard, REST API или Blueprint. Бесплатный web service не поддерживает persistent disk и теряет SQLite при перезапуске, деплое и остановке после простоя. Для сохранения данных нужен платный compute + диск, подтверждённые пользователем. Источники: [Render MCP](https://render.com/docs/mcp-server), [диски](https://render.com/docs/disks), [Free](https://render.com/docs/free).

Во время первоначального исследования Render MCP не был подключён. Позднее MCP заработал с API-ключом, показал workspace и живую схему инструментов. Состояние подключения, сервисов и оплаты в будущей сессии необходимо проверить заново.

## Что уже есть в проекте

- Корневой `Dockerfile` использует Node 24, `HOST=0.0.0.0`, собирает API и веб-клиент, запускает `apps/api/dist/server.js`; `EXPOSE 3000` — декларация образа, а не требование Render слушать именно 3000.
- `apps/api/src/server.ts`: `PORT` по умолчанию 3000, `HOST` по умолчанию `127.0.0.1` (Dockerfile переопределяет на `0.0.0.0`), `DATABASE_PATH` по умолчанию относительный `calendar.sqlite`. `apps/api/src/database/database.ts` открывает SQLite и применяет Drizzle-миграции при открытии; проверить фактическую упаковку миграций и запуск на Render всё равно необходимо.
- `fly.toml` задаёт приложение `call-calendar-k7f2`, Frankfurt, `/data/calendar.sqlite`, volume `/data`, порт 3000 и health check `/api/health`. Это конфигурация Fly, не доказательство текущего состояния Fly и не конфигурация Render. Инструкции проекта требуют проектный skill для любых действий с Fly.
- `origin` указывает на `git@github.com:ignateff/ai-for-developers-project-386.git`; текущая ветка при исследовании — `feat/docker-deploy`. Для Git-backed сервиса предложить HTTPS URL `https://github.com/ignateff/ai-for-developers-project-386`, но владелец должен подтвердить репозиторий, права, целевую опубликованную ветку и commit; локальные незакоммиченные изменения Render не увидит. Не считать текущую ветку автоматически production.

## Подключение OpenCode: будущие действия пользователя

Render рекомендует hosted MCP, который обновляется автоматически; ничего локально устанавливать для него не нужно. Render явно документирует OAuth для ряда клиентов и Bearer API key для headless; OpenCode прямо в списке Render не указан. [Render MCP](https://render.com/docs/mcp-server), [OpenCode MCP V2](https://opencode.ai/v2/docs/mcp-servers).

1. Пользователь выбирает scope и, **если разрешает изменение конфигурации OpenCode**, из нужного проекта выполняет:

   ```sh
   opencode mcp add render --url https://mcp.render.com/mcp
   opencode mcp list
   ```

   Для глобальной конфигурации вместо первой команды использовать `opencode mcp add render --global --url https://mcp.render.com/mcp`. `mcp add` изменяет конфигурацию; `mcp list` проверяет состояние, но подключение может инициировать сетевое соединение. Это не команды настройки Render-сервиса.

2. Если статус `needs authentication`, пользователь в OpenCode открывает `/mcps`, выбирает `render` и завершает OAuth в браузере; затем проверяет `connected`. V2 по умолчанию использует OAuth/PKCE, хранит credentials вне конфигурации. Совместимость OAuth именно этой пары OpenCode/Render в данной сессии **не проверялась**; если обнаружение/регистрация клиента не работают, не подставлять выдуманный client ID. См. [OAuth OpenCode](https://opencode.ai/v2/docs/mcp-servers#oauth) и [Render MCP](https://render.com/docs/mcp-server).
3. Если OAuth недоступен или нужен headless, пользователь сам создаёт Render API key и безопасно передаёт его в окружение процесса OpenCode. Пример альтернативной конфигурации V2, объединять с существующей, не записывая ключ в репозиторий или историю команд:

   ```jsonc
   {
     "$schema": "https://opencode.ai/config.json",
     "mcp": {
       "servers": {
         "render": {
           "type": "remote",
           "url": "https://mcp.render.com/mcp",
           "oauth": false,
           "headers": { "Authorization": "Bearer {env:RENDER_API_KEY}" },
         },
       },
     },
   }
   ```

   См. [remote-конфигурацию OpenCode](https://opencode.ai/v2/docs/mcp-servers#remote) и [Render API keys](https://render.com/docs/api). Scoped keys находятся в early access. Не запрашивать значение ключа в чате, не выводить его в логи. Доступ MCP может менять инфраструктуру; Render не гарантирует, что секреты не попадут в контекст модели. Настроить минимальные возможные разрешения и отдельные подтверждения изменяющих операций.

Render также документирует локальный MCP через Docker или исполняемый файл с `RENDER_API_KEY`; это альтернативы с установкой/запуском локального процесса, не необходимые для hosted варианта. Они не выполнялись. [Инструкция Render](https://render.com/docs/mcp-server#running-locally). Hosted использует Streamable HTTP; проект Render перечисляет поддерживаемые версии протокола, совместимые с обычным initialize handshake OpenCode: [README](https://github.com/render-oss/render-mcp-server#protocol-support).

## Возможности и границы MCP

Ниже — опубликованная схема [README Render MCP](https://github.com/render-oss/render-mcp-server#tools), а не проверенный живой каталог; после подключения нужно прочитать актуальные имена, параметры и разрешения. Возможны отличия hosted версии от `main` репозитория.

| Операция         | Инструмент и последствия                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace        | `list_workspaces` читает список. `select_workspace` меняет выбор в MCP-сессии, но не создаёт ресурс; `get_selected_workspace` читает выбор. README помечает сессионный выбор устаревшим: после подтверждения workspace пользователем передавать `workspaceId` каждому resource tool. При этом основная [страница Render](https://render.com/docs/mcp-server#2-set-your-workspace) всё ещё предписывает выбор workspace. Использовать живую схему; не полагаться на сохранение выбора после reconnect. |
| Обзор            | `list_services`, `get_service`, `list_deploys`, `get_deploy`, `list_events`, `list_logs` (обязателен массив `resource`), `get_metrics` — чтение; логи могут содержать персональные данные и секреты.                                                                                                                                                                                                                                                                                                  |
| Создание         | `create_web_service` **создаёт платный/бесплатный ресурс и запускает первоначальную сборку/деплой**, требует явного согласия. Документированы также static site, cron, Postgres и Key Value; образ из registry через MCP создать нельзя.                                                                                                                                                                                                                                                              |
| Повторный deploy | `trigger_deploy` **изменяет состояние**, с `serviceId` и необязательным `clearCache`; включение очистки может увеличить время сборки. Автодеплой может сработать при push.                                                                                                                                                                                                                                                                                                                            |
| Env              | `update_environment_variables` **заменяет полный список переменных**, не просто добавляет одну; может удалить остальные. Не использовать без согласованного безопасного полного списка и понимания эффекта на deploy.                                                                                                                                                                                                                                                                                 |
| Прочие настройки | MCP не поддерживает произвольное изменение сервиса, scaling, удаление, создание image-backed сервиса или IP allowlist. `update_web_service` по README возвращает ссылку на Dashboard, а не обновляет сервис. Диск и health check в описании параметров `create_web_service` не представлены: использовать Dashboard/API/Blueprint после согласования.                                                                                                                                                 |

`create_web_service`: по README обязательны `name` и `runtime`; для не-Docker ещё `buildCommand` и `startCommand`. Для Docker доступны `dockerfilePath` (по умолчанию `./Dockerfile`), `dockerContext` (по умолчанию `.`), необязательный `dockerCommand` (иначе CMD образа), `repo`, `branch`, `region`, `plan`, `autoDeploy`, `envVars`. Формальная необязательность `repo` не означает, что сборка проекта без доступного исходного кода возможна. Для проекта явно согласовать repo, branch, `runtime=docker`, Frankfurt или другой регион, root context, env и auto-deploy; `autoDeploy` в README по умолчанию `yes`, регион — `oregon`.

**Несоответствие тарифов:** при исследовании README MCP перечислял старые `starter`, `standard` и др., а актуальные [pricing](https://render.com/pricing) и [Blueprint spec](https://render.com/docs/blueprint-spec#plan) использовали `free`, `0.5c-512mb` и другие новые ID. В последующей сессии живая схема MCP включала `free`, однако запрос получил HTTP 402. Проверять актуальную схему, Dashboard и цену до создания; не считать `starter` эквивалентом другого тарифа без подтверждения.

## Порт, диск, миграции и цена

- Render требует слушать `0.0.0.0` и рекомендует порт из `PORT`, по умолчанию `10000`; внешний HTTPS завершается на балансировщике и перенаправляется на один внутренний HTTP-порт. Текущий Dockerfile и сервер должны этому соответствовать без изменения `EXPOSE`, если `HOST` не переопределён. При использовании другого `PORT` проверить фактический bind и логи. [Web services](https://render.com/docs/web-services#port-binding).
- Для SQLite указать `DATABASE_PATH=/data/calendar.sqlite`, смонтировать диск в `/data`, проверить права записи и наличие миграций в образе. Важно: диск доступен только во время работы сервиса; build, pre-deploy и one-off job не видят его. Поэтому миграции этого проекта при открытии БД в стартовом процессе соответствуют модели диска; не переносить их в pre-deploy. Проверить остановку при ошибке миграции и восстановление до production. [Persistent disks](https://render.com/docs/disks#disk-limitations-and-considerations), [deploys](https://render.com/docs/deploys#pre-deploy-command).
- Диск поддерживает только один инстанс, поэтому нет горизонтального масштабирования и zero-downtime при деплое. Диск не разделяется с другими сервисами. Render делает ежедневные snapshots с хранением 7 дней, но предупреждает о риске неконсистентности восстановления custom database: организовать отдельные согласованные с SQLite резервные копии и тест восстановления, не считать snapshot достаточным бэкапом. [Диски](https://render.com/docs/disks#disk-snapshots).
- Free: 15 минут без входящего трафика — остановка, запуск около минуты; 750 часов на workspace в календарный месяц, затем приостановка free web services до следующего месяца; диск и SSH недоступны. Файлы SQLite исчезают при остановке, рестарте и деплое. Free предназначен для демонстрации, не production. При превышении трафика/минут сборки возможны расходы либо ограничения без платёжного метода. [Free](https://render.com/docs/free).
- На дату проверки [pricing](https://render.com/pricing): Hobby $0/месяц за workspace плюс compute; минимальный платный web `0.5c-512mb` $7/месяц, SSD $0.25/GB/месяц; пример 1 GB при полной месячной работе — **около $7.25/месяц**, если доступен такой размер, без налогов и превышений. Hobby включает 5 GB outbound и 500 стандартных pipeline minutes, далее $0.15/GB и $5/1000 минут соответственно. Compute тарифицируется пропорционально времени; проверить условия диска, минимальный размер, валюту, платежи и реальную итоговую цену в Dashboard. Регистрация и применимость оплаты для пользователя не проверены.

## Пошаговый чеклист для проекта

1. **Решение пользователя:** Render только изолированная демо-копия или план миграции? Какой workspace, repo, опубликованный commit/branch, регион, имя, бюджет, платный compute и размер диска? Разрешены ли публичный URL и автодеплой? Для первой проверки предпочесть отдельный сервис с тестовыми данными и отключённым auto-deploy; само создание уже запускает первый deploy.
2. Пользователь подключает Git provider и выдаёт Render доступ к нужному репозиторию; для частного репозитория это обязательно. Public Git URL без подключённого провайдера имеет ограничения: Render рекомендует его для чужих публичных репозиториев, авто-деплои не поддерживаются. Проверить, что выбранная ветка и commit доступны удалённо. [Web services](https://render.com/docs/web-services#deploy-your-own-code), [deploys](https://render.com/docs/deploys#automatic-deploys).
3. Пользователь подключает OpenCode MCP как выше, подтверждает workspace после `list_workspaces`. Агент изучает живую схему, читает список сервисов и избегает дублирования. Согласовываются параметры и отдельное разрешение на создание и расходы. Не передавать секреты в запросы агенту.
4. **Предпочтительный путь для постоянной SQLite:** пользователь создаёт web service через Dashboard с Dockerfile и диском одновременно в Advanced, либо согласованным Blueprint через Dashboard/API. Указать корень monorepo, `./Dockerfile`, `DATABASE_PATH=/data/calendar.sqlite`, диск `/data`, платный план, `/api/health`; не переопределять Docker CMD без необходимости. Blueprint — отдельное инфраструктурное изменение и его синхронизация создаёт/меняет ресурсы; не применять автоматически. См. [Docker](https://render.com/docs/docker), [Blueprint](https://render.com/docs/blueprint-spec), [health checks](https://render.com/docs/health-checks).
5. **Путь через MCP с оговоркой:** после подтверждения вызвать `create_web_service` только если живая схема и цена согласованы. MCP не документирует диск при создании, поэтому первичный deploy может стартовать без него: не направлять реальных пользователей и не записывать ценные данные. Пользователь добавляет диск через Dashboard; сохранение диска запускает новый deploy. Настроить health check и прочие недостающие параметры там же; проверить новое состояние и отсутствие случайной SQLite вне mount. Если точный безопасный порядок или plan не подтверждён — остановиться и использовать пункт 4. [Диски](https://render.com/docs/disks#setup).
6. Агент читает `get_service`, `list_deploys`/`get_deploy`, `list_logs`, при необходимости `list_events`; проверяет commit, успешный запуск, порт и миграции. Проверка публичного `/api/health` и UI — сетевое действие, а не создание ресурса; согласовать, если требуется. Запись тестовых данных — **мутация приложения**, только с отдельным разрешением и тестовыми данными. После согласованного теста проверить сохранение через перезапуск/передеплой: это также мутация с простоем и возможными расходами. Проверить бэкап и восстановление на отдельной тестовой копии.
7. Только после проверки отдельно решать о DNS, пользовательском трафике и CI/автодеплое. При необходимости ручной `trigger_deploy` требует подтверждения; не запускать лишний deploy вслед за автоматическим. [Deploys](https://render.com/docs/deploys).

## Fly и альтернативы

Fly volume и Render disk — независимые хранилища: идентичный путь `/data/calendar.sqlite` не означает общую базу или репликацию. Два активных публичных URL могут принимать конкурирующие бронирования и расходиться; домен/DNS, старые ссылки, кэш DNS, запущенные процессы и несинхронные деплои делают переключение неатомарным. Для миграции нужна отдельно согласованная процедура: остановить запись на старой стороне, сделать консистентную SQLite-копию, безопасно перенести и проверить её, включить запись только на одной стороне, иметь план отката и учитывать новые записи после переключения. Сам факт конфигурации Fly не подтверждает работающий production. Для любых Fly-действий следовать проектному skill, не останавливать Fly автоматически. [Fly volumes](https://docs.fly.io/volumes/overview/), [Render disks](https://render.com/docs/disks).

Другие варианты: остаться на текущем Fly с отдельными SQLite-бэкапами; временно использовать Render Free только для одноразовых тестовых данных; перейти на Render Postgres после изменения приложения и миграции данных — простая замена `DATABASE_PATH` не работает, Free Postgres истекает через 30 дней и не имеет бэкапов ([Free Postgres](https://render.com/docs/free#free-postgres)); или рассмотреть VM с самостоятельной эксплуатацией. Render Dashboard, [REST API](https://render.com/docs/api) и [Blueprints](https://render.com/docs/infrastructure-as-code) — альтернативные способы управления, но их операции создания, синхронизации, изменения и удаления мутируют инфраструктуру и требуют согласия.

## Что осталось неизвестным

- Доступен ли пользователю аккаунт, выбранный workspace, OAuth OpenCode↔Render, Git integration, нужный регион и средства оплаты; фактический live MCP catalog и совместимость тарифных ID.
- Реальная конфигурация, данные и активность Fly; существование сервиса Render; опубликованность конкретного commit; наличие диска, стоимость и доступность пользователям из РФ.
- Работоспособность Docker build и миграций на Render, права `/data`, health check, фактическое время холодного старта и восстановление из бэкапа в этом проекте. Всё требует отдельной проверки после разрешения пользователя.
