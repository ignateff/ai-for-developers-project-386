# Сетевые EOF и таймауты при fly deploy

Дата: 2026-11-02. Область: диагностика и безопасное восстановление после ошибок соединения при сборке Depot и управлении Fly Machines. Источники — официальная документация Fly.io и Docker. Команды ниже — рекомендации, не результаты выполнения; деплой, обращение к приложению и изменение инфраструктуры в рамках этого исследования не проводились.

## Вывод для рассматриваемого случая

По описанию сначала произошёл EOF при handshake с Depot, затем EOF при обращении к Machines API, а более поздний локальный deploy завершился успешно. Это **две разные стадии и два наблюдения**, не доказательство общей первопричины или инцидента Fly/Depot. Успешная локальная сборка и деплой показывают, что использованный позже путь сработал; они не доказывают, что Depot был неисправен, что проблема была только в нём или что сеть между попытками не изменилась. Без временных меток, адресов, полных очищенных логов и состояния сервиса на тот момент причина неизвестна.

`fly deploy` сначала получает/собирает образ, затем обновляет Machines; возможен также release command до обновления приложения ([Deploy an app](https://docs.fly.io/launch/deploy/)). Поэтому EOF при handshake со сборщиком не следует смешивать с EOF при вызове API Machines, публикации образа или ожидании готовности. EOF/timeout сам по себе не устанавливает, дошёл ли запрос до сервера и завершилась ли операция.

## Диагностика без поспешных изменений

1. Зафиксировать время с часовым поясом, версию `fly version`, приложение, стадию и точный endpoint/операцию, идентификаторы Machine, релиз и image digest, полный текст ошибки, наличие VPN/proxy и различия между попытками. Не сохранять токены, заголовки Authorization, секреты и чувствительные данные из debug-логов. Проверить [статус Fly.io](https://status.flyio.net/) и историю инцидентов за соответствующий момент; отсутствие объявления не исключает локальную или частичную проблему.
2. Fly рекомендует `fly doctor` (диагностика WireGuard, IP и Docker), `fly config validate`, `fly logs` и для подробностей `LOG_LEVEL=debug fly deploy`; у команды также есть `--debug` и `--verbose` ([troubleshooting](https://docs.fly.io/getting-started/troubleshooting/), [fly doctor](https://docs.fly.io/flyctl/doctor/), [fly deploy](https://docs.fly.io/flyctl/deploy/)). **Повторный `fly deploy` — мутация**, а не диагностический read-only вызов: запускать только после сверки состояния и при разрешении на деплой. Перед публикацией логов удалить секреты. Fly также рекомендует обновить flyctl; фиксируйте исходную версию до обновления и не предполагайте, что оно решит сетевую проблему.
3. Разделить DNS, TCP/TLS, VPN/proxy и конкретный endpoint по фактической ошибке; при необходимости сравнить с другой разрешённой сетью. Не отключать проверку TLS и не раскрывать токен ради диагностики. Для внешних клиентов публичный Machines API — `https://api.machines.dev`; `http://_api.internal:4280` предназначен для клиентов внутри частной WireGuard-сети Fly и не является универсальной публичной заменой ([Machines API connection](https://docs.fly.io/machines/api/working-with-machines-api/)). Проверка без авторизации не подтверждает права или работоспособность конкретной операции.
4. Прочитать `fly status -a <app>`, `fly machines list -a <app>`, `fly releases -a <app> --image`, `fly checks list -a <app>`, `fly logs -a <app> -n`; для конкретной машины — `fly machine status <id> -a <app>`. Сопоставить состояние, image digest и события всех управляемых Machines с ожидаемым релизом; проверить приложение HTTP-запросом и health checks. `started` не гарантирует здоровый сервис, а остановленная Machine может быть ожидаемым результатом autostop ([troubleshooting](https://docs.fly.io/getting-started/troubleshooting/), [releases](https://docs.fly.io/flyctl/releases/)). Не считать один факт появления релиза доказательством полного rollout.

## Альтернативы сборки и их границы

| Вариант                      | Что меняется                                                                                                                                                                                          | Ограничения и риски                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fly deploy --depot=false`   | Fly рекомендует legacy remote builder при проблемах Depot; сборка остаётся удалённой ([troubleshooting](https://docs.fly.io/getting-started/troubleshooting/#build-hangs-waiting-for-depot-builder)). | Это не локальная сборка и не обход общей проблемы удалённых сборщиков, реестра или Machines API. Может потребоваться создать/использовать удалённый builder; не считать его бесплатным или доступным во всех условиях без проверки текущих лимитов и политики.                                                                                                                                                                                                                                                                            |
| `fly deploy --local-only`    | Сборка локальным Docker daemon; Fly рекомендует при недоступности удалённых сборок ([troubleshooting](https://docs.fly.io/getting-started/troubleshooting/#build-hangs-waiting-for-depot-builder)).   | Нужны работающий Docker и ресурсы, сеть для необходимых base images/dependencies и загрузки образа в registry. Upload может быть медленнее; после сборки по-прежнему нужны registry и управление Machines. Проверить платформу образа и нативные зависимости: локальный ARM-host и целевой Linux могут различаться; эмуляция может быть медленной ([Docker multi-platform](https://docs.docker.com/build/building/multi-platform/)). Не предполагать автоматический выбор нужной архитектуры без проверки конкретной версии и результата. |
| `fly deploy --image <image>` | Использует заранее доступный образ вместо сборки; в документации образ имеет приоритет перед Dockerfile ([Deploy an app](https://docs.fly.io/launch/deploy/#the-build)).                              | Требуется доступный Machines образ с правильной архитектурой и известным digest, доступ к registry и Machines API; конфигурация и release command всё равно применяются. Наличие `[build].image` может сделать выбор `--local-only` не тем экспериментом, который ожидался.                                                                                                                                                                                                                                                               |

Флаги `--wg` и `--https-failover` относятся к связи **с remote builders**, а не являются документированным общим переключателем пути Machines API. По справке flyctl `--https-failover` разрешает fallback на HTTPS при сбое WireGuard; `--recreate-builder` пересоздаёт builder, то есть меняет инфраструктуру, и не должен быть первым диагностическим действием. `--no-cache` отключает build cache, а не исправляет handshake или API EOF ([fly deploy](https://docs.fly.io/flyctl/deploy/)). Проверять актуальные `fly deploy --help` и версию: флаги и значения по умолчанию могут измениться.

## Безопасный повтор и неопределённый результат

- Различать неуспех безопасного чтения и неопределённый исход создающего/изменяющего запроса. При EOF после отправки мутации не повторять её немедленно и параллельно: сервер мог принять её и потерять ответ. Сначала запросить фактическое состояние, события, версии, образ, release command и наличие новых Machines; если API недоступен, дождаться восстановления чтения или эскалировать. Даже частичный rollout требует проверки каждой Machine.
- Для собственных клиентов Machines API применять ограниченное число повторов безопасных чтений с задержкой и jitter, уважать rate limits и не маскировать постоянные ошибки. Это инженерная рекомендация, а не обещание Fly об идемпотентности мутаций. Документация перечисляет HTTP 408, 4xx и 5xx, а также лимит на действие и идентификатор: обычно 1 запрос/с с кратким burst до 3, для Get Machine 5/с с burst до 10; актуальные лимиты проверять в [Machines API](https://docs.fly.io/machines/api/working-with-machines-api/#rate-limits). Не путать транспортный EOF с полученным HTTP 408 или 5xx.
- `--deploy-retries` существует, по умолчанию `auto`; документация команды не гарантирует, что любой повтор безопасен для release command или внешних побочных эффектов. Оценить идемпотентность миграций и других действий, не запускать несколько деплоев одновременно. `--wait-timeout` касается ожидания состояния и здоровья отдельной Machine, а `--release-command-timeout` — release command; увеличение этих значений не является исправлением handshake EOF ([fly deploy](https://docs.fly.io/flyctl/deploy/)).
- При прямой работе с API `GET` возвращает `instance_id`, `image_ref`, состояние и события; создание может генерировать имя, а update работающей Machine перезагружает её и требует полного config. У API есть leases для исключительной модификации и `current_version` в update; это инструменты координации, но не доказательство идемпотентности произвольного повтора. Проверить актуальный контракт прежде чем создавать собственную оркестрацию ([Machines resource](https://docs.fly.io/machines/api/machines-resource/)). Не снимать чужой lease и не уничтожать Machine/volume ради устранения сетевого EOF.
- Если после сверки нужен повтор или откат, это отдельное изменение production: выбрать подходящий образ и конфигурацию, оценить downtime и сохранность данных. Откат старого образа не откатывает миграции, `fly.toml` или секреты; старый образ может быть удалён из registry ([rollback guide](https://docs.fly.io/blueprints/rollback-guide/)). Проверить состояние после завершения. Для SQLite на volume не пересоздавать инфраструктуру и не переключать регион без отдельного плана данных.

**Что остаётся неизвестным:** точная причина обоих EOF, были ли приняты какие-либо мутации, совпадали ли образы и конфигурация попыток, состояние Depot/Fly в момент ошибки и доступность соответствующих диагностических журналов. Официальные источники описывают механизмы и варианты обхода, но не устанавливают причину конкретного инцидента.
