# Генерация серверных артефактов Fastify из контракта

Дата: 2026-11-01. Исследование по документации и исходникам авторов, без установки генераторов и запуска прототипа. Это рекомендация для проверки, не ADR и не подтверждение совместимости конкретной версии с нашим контрактом.

## Контекст и решение

Источник истины — [TypeSpec](../../contract/main.tsp); [tspconfig.yaml](../../tspconfig.yaml) выдаёт [OpenAPI 3.0.0](../../generated/openapi/openapi.yaml), а [Orval](../../contract/orval.config.ts) генерирует fetch-SDK. API использует Fastify 5.12.7, ESM и TypeScript ([package.json](../../apps/api/package.json)). Регистрация обработчиков разделена по доменам в [app.ts](../../apps/api/src/app.ts); сверка методов и путей уже есть в [contract-check.ts](../../apps/api/src/contract-check.ts). [Контрактные тесты](../agents/testing.md) проверяют каждый сценарий ответа по реальному HTTP.

**Рекомендация: пока оставить существующие маршруты и тесты; первым кандидатом на отдельный небольшой эксперимент выбрать `fastify-openapi-glue` в режиме плагина**, если цель — устранить ручное дублирование путей и схем. Это непосредственно использует уже генерируемый OpenAPI, но создаёт маршруты при запуске, а не выдаёт типизированные TypeScript-обработчики. Если нужны только статические типы, рассмотреть `openapi-typescript` отдельно: он не решает регистрацию маршрутов и runtime-валидацию. Ни один вариант не считать готовым к внедрению до проверок ниже.

Причина осторожности: в [booking routes](../../apps/api/src/bookings/routes.ts) одновременно собираются локализованные ошибки полей, выполняются trim и бизнес-проверки; [app.ts](../../apps/api/src/app.ts) задаёт общий формат ошибок. Ранняя схемная валидация может не допустить запрос до этих проверок и изменить ответ, даже если итоговая ошибка всё ещё имеет статус 400. Это риск, а не обнаруженная в эксперименте регрессия.

## Варианты

### `fastify-openapi-glue`: OpenAPI → маршруты и схемы Fastify

[README проекта](https://github.com/seriousme/fastify-openapi-glue/blob/master/README.md) описывает плагин: он принимает OpenAPI v2/v3 и объект обработчиков или `operationResolver`, конфигурирует маршруты и схемы, связывая операции с ручными обработчиками. Путь доменных сервисов, зависимости и бизнес-логику всё равно надо реализовать самим. Отдельный CLI генерирует JS-проект с плагином, заготовкой handlers и тестовым каркасом либо standalone JS; это **не генерация TypeScript-сервера**, а повторный запуск CLI может перезаписать существующие файлы. Поэтому генерация проекта поверх `apps/api` неприемлема.

В опубликованном [package.json репозитория](https://github.com/seriousme/fastify-openapi-glue/blob/master/package.json) для версии 4.12.0 указаны ESM, Node >=20, декларации типов и Fastify 5.12.7 как devDependency. Это свидетельствует о тестовой конфигурации проекта, но не доказывает совместимость именно нашего приложения и всего контракта. Плагин — runtime-зависимость; необходимо проверить загрузку YAML в собранном приложении и доставку OpenAPI при деплое. `operationId` в нашем OpenAPI уже присутствуют, например `createBooking`; проверить уникальность и устойчивость имён всех операций, обработку отсутствующего handler и внедрение `storage`/часов при регистрации.

Ограничения автора: Fastify по умолчанию приводит типы; поддержка cookies, multipart, особых query и content types может требовать дополнительной настройки; OpenAPI 3.1/draft 2020-12 требует отдельной конфигурации ([README, Notes](https://github.com/seriousme/fastify-openapi-glue/blob/master/README.md#notes)). Текущий документ — 3.0.0, но это не гарантия корректного преобразования `$ref`, форматов и всех ответов. По [документации Fastify](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/) схемы ответа используются для сериализации, а не являются заменой независимой проверки ответа по OpenAPI; схема может изменить сериализуемые данные.

### `openapi-typescript`: только типы

[Документация](https://openapi-ts.dev/introduction) указывает поддержку OpenAPI 3.0/3.1 и генерацию runtime-free TypeScript-типов для путей, тел и ответов. Ими можно типизировать собственные адаптеры Fastify без нового механизма маршрутизации. Но схемы выполнения, обработчики, проверки наличия всех маршрутов и сопоставление статусов/заголовков с типами нужно проектировать отдельно; один импорт типов не доказывает соответствие ответа HTTP-контракту. Это менее рискованная по runtime альтернатива, но не полноценный генератор сервера.

### `@typespec/http-server-js`: напрямую из TypeSpec, но не Fastify

[README эмиттера TypeSpec](https://github.com/microsoft/typespec/blob/main/packages/http-server-js/README.md) маркирует пакет как highly experimental. Он генерирует модели, интерфейсы сервисов, маршрутизатор и функции операций для Node HTTP; опционально доступен Express middleware. Документация говорит, что функции разбирают запрос и **могут** выполнять валидацию; нельзя предполагать полную валидацию всех ограничений. Документированного Fastify-адаптера там нет. Это перспективный прямой TypeSpec-вариант, но интеграция потребует самостоятельного адаптера или смены HTTP-стека; сейчас не предпочтителен. Версию, совместимость с TypeSpec 1.17.0 и поддержку нашего контракта необходимо проверить отдельно.

### Другие генераторы

В [списке OpenAPI Generator](https://openapi-generator.tech/docs/generators/) среди server generators есть `nodejs-express-server` и `typescript-nestjs-server`, но нет указанного Fastify server generator. Не следует путать клиентский `typescript-node` с сервером Fastify. Собственные шаблоны возможны, но их поддержка и проверка соответствия контракта лягут на проект.

[`openapi-fastify-codegen`](https://github.com/ozonep/openapi-fastify-codegen) описывает одноразовую генерацию JavaScript/Fastify и валидацию, а не типизированные обработчики; [GitHub API репозитория](https://api.github.com/repos/ozonep/openapi-fastify-codegen) показывает последний push в 2022 году. Совместимость с Fastify 5 и нашим OpenAPI не установлена; риск сопровождения и миграции выше, поэтому не первый кандидат.

## Критерии эксперимента до внедрения

1. В изолированном прототипе зафиксировать версии и сгенерировать текущий OpenAPI обычной цепочкой; проверить Fastify 5, Node и ESM, успешный запуск и остановку с SQLite. Не генерировать поверх ручных файлов. Сохранить разделение доменных сервисов и явную передачу зависимостей.
2. Проверить все методы/пути, `operationId`, отсутствие и дублирование обработчиков, `/api/health`, `$ref`, обязательные и необязательные body/path/query/header, UTC date-time, целые числа, ограничения строк и 204 без тела. Особо проверить `Idempotency-Key`, `If-Match`, `ETag`, `Cache-Control` и все объявленные статусы. Сравнить фактические ответы и заголовки с существующим поведением по реальному HTTP.
3. Проверить несколько одновременных ошибок полей, пустые и отсутствующие поля, пробелы, некорректные даты, типы и лишние поля; зафиксировать влияние Ajv coercion/removal/defaults, порядок проверки и совместимость локализованного `fields`. Учесть, что Fastify по умолчанию использует Ajv для входа и `fast-json-stringify` для ответа ([документация](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)). При несовпадении явно решить, можно ли сохранить поведение; не менять API молча.
4. Сохранить реальные HTTP contract-тесты каждого сценария и route-guard; дополнить тестами семантики и бизнес-инвариантов. Типы и генерация не доказывают корректность авторизации, идемпотентности, ошибок БД или содержимого ответа. Сравнить поведение существующих тестов до и после, в том числе конкурентные сценарии бронирования.
5. При выборе build-time генерации отделить перезаписываемый вывод в `generated/` от ручного кода, обеспечить воспроизводимость и обновить [check-generated.mjs](../../scripts/check-generated.mjs), если потребуются дополнительные входы или зависимости. Учитывать правила `mise` и lockfile из [AGENTS.md](../../AGENTS.md). При runtime-плагине предусмотреть доставку OpenAPI и проверку запуска собранного приложения. Ничего из этого в рамках исследования не реализовано.

**Оговорки:** документация веток и список генераторов могут измениться; зафиксировать конкретные версии и повторно проверить источники при внедрении. Поиск через веб-интеграцию был недоступен (HTTP 403); исследование опирается на непосредственно доступные первичные источники и не является исчерпывающим обзором экосистемы.
