# Ретроспектива: параллельные worktree и проверки

Дата: 2026-11-02. Контекст: параллельная работа над задачами #42, #51–#54 и интеграция в PR #55. Это **предложения, а не утверждённый план работ**: возвращаться к ним по мере необходимости.

## Главное наблюдение

Параллельная реализация позволила вести независимые задачи одновременно, но одновременные полные проверки столкнулись с таймаутами запуска dev-серверов и оставшимися тестовыми процессами. После перехода к последовательным полным прогонам проверки прошли. Нагрузка и конкуренция — возможные причины; точная причина каждого таймаута не установлена.

На момент ретроспективы, 2026-11-02, полный `mise run check` запускался в CI и через pre-commit и pre-push hooks; он включал Vitest и Playwright. Отдельные порты `E2E_API_PORT` и `E2E_WEB_PORT` изолируют серверы Playwright, но не тесты запуска dev-серверов с временными checkout и daemon-процессами.

**Текущие hooks:** после изменения по [#60](dev-hook-timeouts.md#реализация-по-issue-60) pre-commit и pre-push запускают только `mise run check:quick`, а не полный набор. Актуальный состав и порядок проверок — в [инструкции по тестированию](../agents/testing.md) и [hk.pkl](../../hk.pkl).

**Практический вывод:** при следующей параллельной работе запускать целевые тесты параллельно, а полные проверки — последовательно. Останавливать только собственные тестовые процессы; незакоммиченные и игнорируемые данные проверять перед удалением worktree.

## Предложения на будущее

1. **Устойчивость параллельных проверок.** Если таймауты повторятся, исследовать `scripts/dev.test.ts` под нагрузкой, изоляцию daemon-процессов и очистку после прерванных прогонов. Не обходить hooks и не увеличивать таймауты без установления причины.
2. **Доказательность тестов гонок.** При ревью асинхронных тестов различать доставку ответа и его обработку приложением; проверять, что тест способен обнаружить заявленную регрессию. Дополнительная проверка устаревшего ответа слотов отслеживается в [#56](https://github.com/ignateff/ai-for-developers-project-386/issues/56).
3. **Исторические инциденты.** Перед формулировкой критерия «установить причину» проверить доступность необходимых логов. В [#42](https://github.com/ignateff/ai-for-developers-project-386/issues/42) воспроизведён возможный механизм `DATABASE_BUSY`, но причина конкретного старого CI-сбоя не доказана.
4. **Обзор UI.** При следующем обзоре проверить favicon, заголовок вкладки, состояния ошибок и неподтверждённые обещания. Отсутствующую фавиконку обнаружил пользователь после первоначального исследования; задача на неё вошла в PR #55.
5. **Навыки деплоя.** При следующей работе с Fly.io перепроверить проектный скилл по актуальной документации: согласование платных ресурсов, региона и хранения; для ошибок провайдера различать ответ конкретного аккаунта и общие условия тарифа. Не менять live-ресурсы без согласия владельца.

## Что сработало

- На момент ретроспективы общие проверки были подключены и локально, и в CI; второй аналогичный guardrail не потребовался.
- Расхождение макета с требованием об отсутствии писем поднято и согласовано с владельцем до реализации.
- Агентские изменения изолировались в worktree и коммитились перед интеграцией; непроверенную работу не объявляли завершённой.
- Дополнительное ревью выявило ограничение теста гонки до перевода PR в готовность.
