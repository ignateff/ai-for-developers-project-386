# Таймауты запуска dev в Git hook: источники и гипотезы

Дата исследования: 2026-11-02. Источники — официальная документация и код проекта; локальные наблюдения приведены отдельно ниже. Причина конкретного сбоя не установлена. Документация ниже описывает текущие версии инструментов: перед применением следует сверить установленные версии и их документацию.

## Локальные наблюдения

- Полный pre-commit ранее прошёл: 80 тестов и 24 browser-теста. При последующем pre-push два теста `scripts/dev.test.ts` завершились `spawnSync mise ETIMEDOUT` на запуске `mise run dev` (строки 49 и 106). Вызовы имеют собственный лимит 60 секунд; тайм-аут команды hook не является причиной этих двух ошибок.
- Повтор `mise run test -- scripts/dev.test.ts` был остановлен внешним лимитом 180 секунд до итогового отчёта: из него нельзя определить точную стадию задержки.
- Узкий запуск `mise run test -- scripts/dev.test.ts -t 'uses an explicitly requested web port'` показал `1 passed`, но suite завершился ошибкой в `afterAll`: `mise daemons stop` сообщил `no matching project daemons` для checkout, созданного вне теста и не использованного при фильтрации. Это отдельный дефект cleanup, не доказанная причина исходного `ETIMEDOUT`. Ошибка внутри цикла cleanup может прервать обработку остальных checkout (см. `scripts/dev.test.ts:22-37`).
- Демоны основного checkout были запущены на момент проверки; их наличие само по себе не объясняет сбой временных checkout. Не останавливать их без согласия владельца.

**Вывод:** точная причина тайм-аутов пока не найдена; быстрый детерминированный воспроизводитель исходного симптома отсутствует. Для следующего эксперимента измерить стадии `scripts/dev-start.mjs` в изолированном временном checkout и сопоставить с логами только его демонов; не удалять пользовательские процессы или данные. Отдельно исправить cleanup, чтобы выбор одного теста не порождал ложный отказ suite и не прерывал очистку остальных checkout.

## Дополнительное исследование: измерение стадий

**Итог:** исходный `ETIMEDOUT` не воспроизведён и его первопричина **не доказана**. На этой машине есть измеренная многосекундная стоимость нескольких операций управления демонами, в том числе вне readiness; суммарно она существенно расходует 60-секундный бюджет. Это правдоподобный вклад, а не доказательство конкретного сбоя или того, что каталоги состояния вызвали задержку.

### Что именно делает код

- `mise.toml:43-45` запускает `node scripts/dev-start.mjs`; это не декларативная зависимость задачи от `daemons`. Скрипт последовательно делает локальный `mise daemons ls --json`, глобальный `pitchfork list --json`, `mise daemons start api`, ещё один локальный список перед web, `mise daemons start web`, затем импортирует `scripts/dev-url.mjs`. Последний снова вызывает локальный список и глобальный `pitchfork list --json`. `scripts/dev-target.mjs` внутри команды web дополнительно вызывает локальный список. На каждом шаге результат предыдущего синхронно ожидается.
- `mise.toml:125-134` задаёт HTTP readiness через `curl`, для web также зависимость от API. Измеренные `start` включают не только время приложения и readiness, но и накладные расходы mise/pitchfork, зависимости и прочие внутренние действия; отделить их по приведённым данным нельзя. Vite `ready in 97 ms` не является временем всего запуска web.
- В исходниках именно установленной версии [pitchfork v2.32.3: list.rs](https://github.com/jdx/pitchfork/blob/v2.32.3/src/cli/list.rs) вызов `list` подключается к supervisor и получает объединённый список; [daemon_list.rs](https://github.com/jdx/pitchfork/blob/v2.32.3/src/daemon_list.rs) читает состояние и реестр namespace и загружает конфигурации зарегистрированных namespace, включая при фильтрации. Это устанавливает потенциальную зависимость работы списка от общего состояния, но не измеряет вклад реестра на данной машине и не связывает его с каталогами mise. Просто добавить `--project` не гарантирует устранения этих обходов.
- Ошибка `spawnSync mise ETIMEDOUT` на строках 49 и 106 доказывает истечение лимита внешнего синхронного вызова Node, но без сохранённых логов и меток не показывает, какой вложенный вызов в тот момент выполнялся. Не доказаны ни удержание pipe потомком, ни конфликт портов, ни непосредственная вина Git hook.

### Как повторить безопасно

1. Создать **новый** временный каталог через `mkdtemp`, скопировать проект с фильтром из `makeCheckout()` и создать те же три симлинка на `node_modules`; задать `MISE_TRUSTED_CONFIG_PATHS` этому каталогу. Убедиться по `mise daemons ls --json`, что оба daemon-а копии `available`, а их `root` указывает на неё. Не запускать тестовый `afterAll` для измерения.
2. Из cwd копии измерить `mise daemons ls --json`, `mise exec -- pitchfork list --json`, `mise daemons start api`, `mise daemons ls --json`. Для следующей стадии записать пустую строку в `calendar-proxy-target` внутри `state_dir` web из JSON, затем измерить `mise daemons start web`, `mise exec -- node scripts/dev-url.mjs` и повторный `mise run dev`. Использовать `spawnSync` с `encoding: 'utf8'`, `stdio: 'pipe'`, `timeout: 35000` для каждой стадии и печатать elapsed, status, signal, error, stdout/stderr. Это измерение команд, а не профилирование внутренних функций.
3. Для отдельного замера полного холодного запуска повторить с **другой** новой копией: `spawnSync('mise', ['run', 'dev'], { cwd, env, encoding: 'utf8', stdio: 'pipe', timeout: 60000 })`. Измерять с `performance.now()`. Не считать повторное использование работающего глобального supervisor холодным стартом supervisor.
4. В `finally` адресно остановить `mise daemons stop web` и `mise daemons stop api` из cwd именно своей копии, с отдельным timeout; проверить JSON на отсутствие `running` и только тогда удалить собственную копию. При timeout/неясном состоянии сохранить каталог для диагностики; не вызывать глобальный stop/prune и не удалять чужие state dirs. Учесть, что симлинки на `node_modules` разделяют кэши с исходным checkout.

Следующий причинный эксперимент — сравнить идентичные запуски с контролируемым изолированным реестром/состоянием pitchfork и с заполненным синтетическими **собственными** записями, не изменяя пользовательский supervisor; сначала проверить по документации и исходникам все пути сокета, state и registry. Затем профилировать задержку и собрать несколько повторов; пока такого сравнения нет, очистка пользовательского состояния или увеличение лимита не обоснованы.

## Факты из документации

### mise и pitchfork

- `mise run` загружает окружение и инструменты задачи, сначала выполняет её зависимости, а независимые задачи может выполнять параллельно. `--jobs` ограничивает параллелизм, `--raw` подключает стандартные потоки напрямую и выполняет по одной задаче. Общий `--timeout` и индивидуальный timeout задачи — разные ограничения; при ошибке по умолчанию mise останавливает выполняющиеся задачи. [mise: Running tasks](https://mise.jdx.dev/tasks/running-tasks.html).
- Поддержка daemons в mise экспериментальна. Задача с `daemons` ждёт готовности нужных сервисов до запуска тела; уже работающие сервисы переиспользуются и продолжают жить после выхода задачи. `mise daemons start` тоже ждёт готовности и может установить отсутствующие инструменты, включая pitchfork. Это поведение относится именно к описанному механизму daemons, а не автоматически ко всякой задаче с именем `dev`. [mise: Daemons](https://mise.jdx.dev/daemons.html).
- Pitchfork управляет сервисами через постоянный supervisor; процессы могут пережить CLI. Запущенный процесс не обязательно готов: зависимости ждут readiness, независимые сервисы стартуют параллельно. Без явной проверки daemon считается готовым после трёх секунд работы. [Pitchfork: How it works](https://pitchfork.jdx.dev/concepts/how-it-works.html).
- При проблемах readiness документация предлагает проверить фактический адрес, порт, код ответа и команду проверки; динамический порт и жёстко заданный URL могут не совпадать. Если все проверки истекли, startup возвращает код 124. Для диагностики рекомендуются status и логи, а не удаление состояния. [Pitchfork: Troubleshooting](https://pitchfork.jdx.dev/troubleshooting.html).

### Node.js и Vitest

- `execFileSync` блокирует event loop вызывающего Node.js-процесса; без `shell` исполняемый файл запускается напрямую. Его `timeout` по умолчанию равен 0; при установленном timeout отправляется `killSignal` (по умолчанию SIGTERM), но синхронный вызов ждёт завершения процесса, в том числе если тот перехватил сигнал и не вышел. При ошибке выбрасывается исключение с результатами процесса. [Node.js: execFileSync](https://nodejs.org/api/child_process.html#child_processexecfilesyncfile-args-options).
- По умолчанию у дочерних процессов есть pipes для stdio; их ёмкость ограничена. Для захватываемого вывода также существует `maxBuffer`; его превышение — отдельная ошибка, не доказательство таймаута. `cwd`, `env` и `PATH` влияют на запуск. Унаследованные дескрипторы долгоживущих потомков могут мешать закрытию потоков: событие `close` отличается от `exit` и наступает после закрытия stdio. Сам факт существования daemon **не доказывает**, что он удерживает pipe данного запуска. [Node.js: child processes](https://nodejs.org/api/child_process.html#child-process), [stdio](https://nodejs.org/api/child_process.html#optionsstdio), [close](https://nodejs.org/api/child_process.html#event-close).
- Текущая документация Vitest указывает в Node.js дефолты `testTimeout` 5 с и `hookTimeout` 10 с; они относятся соответственно к тесту и тестовому hook, а не к Git hook или отдельному timeout subprocess. Значения могут быть переопределены; 0 отключает соответствующее ограничение. [Vitest: testTimeout](https://vitest.dev/config/testtimeout), [hookTimeout](https://vitest.dev/config/hooktimeout).
- Поскольку `execFileSync` блокирует event loop, нельзя полагаться на таймер Vitest как на жёсткую внешнюю границу времени синхронного вызова; нужно отдельно измерять фактический процесс и его timeout. Это вывод из документированной синхронной блокировки Node.js, а не утверждение о конкретном внутреннем механизме всех версий Vitest.
- Vitest поддерживает настройку числа workers; отключение `fileParallelism` устанавливает `maxWorkers` в 1. Это инструмент для эксперимента с конкуренцией, но не доказательство ускорения или гарантии изоляции внешних ресурсов. [Vitest: fileParallelism](https://vitest.dev/config/fileparallelism), [maxWorkers](https://vitest.dev/config/maxworkers).

### Git pre-push

- Git передаёт pre-push имя и адрес remote как аргументы, а обновляемые refs — через stdin; ненулевой exit code отменяет push. В обычном non-bare репозитории Git запускает hook из корня worktree; исключения для некоторых серверных push-hooks не включают client-side pre-push. Git также экспортирует переменные репозитория, которые могут повлиять на вложенные Git-команды в другом worktree. [Git: githooks](https://git-scm.com/docs/githooks#_pre_push).
- Локальные проверки не являются серверной гарантией: `git push --no-verify` обходит pre-push. Для обязательного контроля нужен независимый CI/серверный gate. [Git: git-push](https://git-scm.com/docs/git-push#Documentation/git-push.txt---no-verify).

## Проверяемые гипотезы — не установленные причины

1. **Холодный старт или readiness превышает доступный бюджет.** Сравнить длительности холодного и повторного запуска, отдельно время установки инструментов, старта supervisor, сервисов и readiness; сопоставить с реальными timeout каждого слоя. Признак в пользу — задержка находится до readiness, подтверждается статусом/логами; уже готовый запуск заметно быстрее. Код 124 полезен только вместе с источником ошибки.
2. **В hook и интерактивном запуске различается окружение.** Сопоставить безопасный набор переменных, `PATH`, `cwd`, версии, настройки профиля и доступность stdin/TTY, не выводя секреты. Признак — воспроизводимое различие при изменении одного параметра; Git-переменные особенно важны при обращении к другому worktree.
3. **Неверная readiness-проверка или конкуренция за порт.** Сверить адрес и фактический порт конкретного сервиса с его readiness endpoint, проверить ответ и логи; сравнить изолированные и параллельные запуски. Наличие занятого порта само по себе не объясняет сбой без связи с выбранным адресом и проверкой.
4. **Долгоживущий потомок удерживает захваченный stdio.** Сравнить время выхода непосредственного CLI и закрытия потоков, исследовать владельцев дескрипторов, затем в изолированном воспроизведении сравнить варианты перенаправления stdio. Признак — CLI уже вышел, а дескриптор потомка остаётся открытым; без этого нельзя приписывать задержку pitchfork.
5. **Перегрузка от параллельных проверок.** Измерить поэтапное время и частоту отказов при ограничении jobs/workers и без него, при одинаковом состоянии сервисов. Положительный результат показывает влияние конкуренции, но не обязательно её первопричину.
6. **Ошибочно определён виновник timeout.** Сохранить полное сообщение, exit code/signal, stdout/stderr и временные метки. Различить timeout readiness, mise, `execFileSync`, Vitest test/hook и внешнего процесса; отдельно исключить `maxBuffer` и ошибки запуска. Не повышать все лимиты одновременно.

## Варианты надёжной и быстрой проверки pre-push

Это предложения для оценки, а не установленные требования проекта:

- Оставить в pre-push ограниченный по времени, детерминированный набор быстрых проверок без обязательного старта общего dev-окружения; полноценные интеграционные и браузерные сценарии запускать отдельной явной задачей и в обязательном CI. Перед изменением состава согласовать покрытие: быстрый subset не эквивалентен полному набору.
- Разделить unit/contract и проверки жизненного цикла dev: последние тестировать отдельно, с изолированными ресурсами, явной readiness и очисткой только собственных процессов. Не останавливать общие пользовательские daemon-процессы ради ускорения hook.
- Для внешних процессов предпочесть асинхронное ожидание с отдельным ограничением времени, сохранением диагностики и продуманным завершением процесса и его потомков; сам timeout/посылка сигнала не гарантирует очистку supervisor или всех потомков. Для реальной верхней границы учитывать внешний watchdog и безопасную эскалацию.
- Замерять cold/warm и p95 длительности, проверять не только успех, но и контролируемые отказы/очистку. Параллелить независимые проверки лишь после подтверждения отсутствия конфликтов. Кэш допустим только с полными входами и корректной инвалидизацией; иначе CI должен оставаться полным независимым gate.
- Если hook анализирует refs, корректно обработать несколько строк, создание и удаление refs и не считать текущее состояние worktree идентичным отправляемому commit. Не давать вспомогательным командам случайно потреблять stdin с данными pre-push.

## Реализация по issue #60

### Изоляция

В `scripts/dev.test.ts` каждому запуску suite выделяются собственные `MISE_STATE_DIR`, `PITCHFORK_STATE_DIR`, `PITCHFORK_CONFIG_DIR` и `PITCHFORK_LOGS_DIR`. Одного state-dir Pitchfork недостаточно: registry хранится в пользовательском config; socket зависит от state-dir. Источники установленной версии: [env.rs](https://github.com/jdx/pitchfork/blob/v2.32.3/src/env.rs), [extra_configs.rs](https://github.com/jdx/pitchfork/blob/v2.32.3/src/extra_configs.rs), [mise daemon fixture](https://github.com/jdx/mise/blob/v2026.10.23/e2e/cli/test_daemons_pitchfork). `MISE_DATA_DIR` не меняется: установленные инструменты остаются общими.

Sandbox имеет короткий уникальный путь под home: [Unix socket ограничен длиной пути](https://github.com/jdx/pitchfork/blob/v2.32.3/src/ipc/mod.rs). Proxy, web и API интерфейсы supervisor отключены через env. Унаследованные порты приложения и UI-порт Pitchfork удаляются из тестового окружения; портовые overrides задаются конкретным сценарием. Изоляция не разделяет TCP-порты и кэши `node_modules`, поэтому это не полная системная песочница. Системная конфигурация `/etc/pitchfork/config.toml` также остаётся общей.

### Изменения и измерения

- Реальные семь dev-сценариев сохранены. Вызовы CLI стали асинхронными, с выводом stdout/stderr, cwd, кода завершения и состояния демонов при ошибке. Тайм-аут старта остался **60 с**, а не увеличен. `scripts/test-command.test.ts` проверяет успешное выполнение, ненулевой выход и тайм-аут, включая процесс, игнорирующий SIGTERM. Для тестовых команд используется SIGKILL при истечении лимита; это завершает непосредственный процесс, а отдельные демоны очищаются fixture, не глобальным kill. Не считать остановку CLI доказательством остановки всех его потомков.
- Checkout создаются по требованию. Cleanup обрабатывает каждый checkout, проверяет отсутствие PID и терминальные статусы, затем останавливает только собственный supervisor. Статус `errored` без PID допустим после намеренного отказа web. При ошибке очистки соответствующие ресурсы сохраняются для диагностики; пользовательский supervisor не останавливается.
- Фильтр `mise run test -- scripts/dev.test.ts -t 'uses an explicitly requested web port'`: **1 passed, 6 skipped**, весь запуск **2,69 с**, включая cleanup.
- `mise run test -- scripts/dev.test.ts scripts/test-command.test.ts`: **11 passed**, **11,83 с**.
- Повтор `mise run test -- scripts/dev.test.ts`: **7 passed**, **11,21 с**. Это несколько успешных измерений на одной машине, не p95 и не доказательство точной первопричины старых EOF/тайм-аутов. Изоляция и асинхронный запуск менялись вместе; их вклады не разделены причинным экспериментом.
- Local hooks переключены на `mise run check:quick` (lint, форматирование, типы). Полный `mise run check` и CI остаются полными. Проверка типов теперь включает TypeScript-файлы `scripts/`.
- Итоговый `mise run check` прошёл целиком: **84 Vitest-теста за 12,89 с**, **24 browser-теста за 19 с**, проверки типов, формата, контракта, генерации, сборки и workflow. Семь lifecycle-сценариев входят в эти 84 теста, а не исключены из набора. Пользовательские API/web демоны после прогона остались `running`.

### Обязательность CI

Readonly GitHub API первоначально показал `main.protected=false`, отсутствие rulesets и required status checks. С разрешения пользователя настроена и повторно прочитана защита `main`: обязательный PR, обязательный check `check` от GitHub Actions (`app_id=15368`), strict/up-to-date, запрет force-push и удаления. Обязательные approvals не добавлены; `enforce_admins=false`, то есть администраторы сохраняют обход. Настройка сделана через [Branch protection API](https://docs.github.com/en/rest/branches/branch-protection#update-branch-protection), не является частью git diff и может измениться независимо от кода.
