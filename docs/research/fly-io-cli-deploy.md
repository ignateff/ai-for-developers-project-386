# Деплой Dockerfile-приложения на Fly.io через flyctl

Дата: 2026-11-02. Исследование для будущего agent-скилла, который деплоит одноконтейнерное Node.js-приложение (Fastify отдаёт API + собранный фронтенд, SQLite-файл через `DATABASE_PATH`, прослушивание порта из `PORT`) на Fly.io Machines через CLI `fly`. Источники: только официальная документация docs.fly.io плюс вывод `--help` локально установленного CLI (`~/.fly/bin/fly`, flyctl v0.5.1, darwin/arm64, сборка 2026-10-29). Мутирующие команды не выполнялись.

> Примечание: у Fly.io уже есть официальный инструментарий для агентов — `fly setup agent` устанавливает «Fly skills» и hosted MCP-сервер для coding-агентов, а `fly skills install` ставит их для конкретного агента ([Agent skills](https://docs.fly.io/model-context-protocol/agent-skills/), [Fly agent setup](https://docs.fly.io/model-context-protocol/setup-agent/)). Будущий скилл должен учитывать их существование и либо дополнять их, либо уступать им.

## 1. Установка и аутентификация

**Установка.** `brew install flyctl` на macOS с Homebrew; иначе скрипт `curl -L https://fly.io/install.sh | sh` (macOS/Linux) или `iwr https://fly.io/install.ps1 -useb | iex` в PowerShell на Windows. Скрипт ставит в `~/.fly` и печатает строки PATH для добавления в rc-файл шелла ([Install flyctl](https://docs.fly.io/flyctl/install/)).

**Интерактивный вход.** `fly auth signup` создаёт аккаунт; `fly auth login` выполняет вход ([Quickstart](https://docs.fly.io/getting-started/launch/)). Справка CLI (v0.5.1): `fly auth login` по умолчанию использует браузер; `--email/--password` (или `-i`) для входа по email/паролю, `--otp` для одноразового пароля, а `--code <code>` завершает браузерный вход, ожидающий подтверждения, — задокументированный запасной путь, когда «браузер на другой машине, или ожидающая команда была остановлена» (`fly auth login --help`).

**Проверка identity.** `fly auth whoami` печатает текущего аутентифицированного пользователя/service identity; `-j` для JSON (`fly auth whoami --help`).

**Токены для CI/неинтерактивной работы.** Переменная окружения `FLY_API_TOKEN`; каждая команда flyctl также принимает глобальный флаг `-t/--access-token` (глобальные флаги в любом `--help`). Токены — это макаруны с предопределёнными скоупами; создаются через `fly tokens create`:

- `fly tokens create deploy [-a app] [-x 48h] [-n name]` — deploy-токен на приложение; срок по умолчанию 20 лет, документация рекомендует более короткий (`fly tokens create deploy --help`, [Access tokens](https://docs.fly.io/security/tokens/)).
- `fly tokens create org` — деплой всех приложений организации; `fly tokens create readonly` — read-only токен организации; `fly tokens create ssh` / `machine-exec` для более узких скоупов ([Access tokens](https://docs.fly.io/security/tokens/)).
- Управление: `fly tokens list` (добавьте `--scope org` для токенов организации) и `fly tokens revoke <id>` ([Access tokens](https://docs.fly.io/security/tokens/)).
- Рецепт для GitHub Actions хранит deploy-токен в секрете репозитория `FLY_API_TOKEN` и выполняет `flyctl deploy --remote-only` с `superfly/flyctl-actions/setup-flyctl@master` ([Continuous Deployment with GitHub Actions](https://docs.fly.io/launch/continuous-deployment-with-github-actions/)).
- **Не используйте** вывод `fly auth token` как CI-токен — он короткоживущий и всемогущий; документация явно отзывает эту рекомендацию ([Access tokens](https://docs.fly.io/security/tokens/)).

**Выводы для скилла:** Прежде всего проверять наличие flyctl на PATH (включая `~/.fly/bin/fly`); `fly auth login` — шаг с человеком в цикле (браузерный флоу); для headless-запусков принимать `FLY_API_TOKEN` / `-t`. Никогда не печатать и не сохранять значения токенов. Не вызывать `fly auth token` для автоматизации.

## 2. `fly launch`

**Что делает.** Запущенный из директории с исходниками, `fly launch` создаёт приложение, сканирует исходный код, находит или создаёт способ сборки Docker-образа, записывает `fly.toml` и (если не запрещено) деплоит ([Create an app with Fly Launch](https://docs.fly.io/launch/create/), [Quickstart](https://docs.fly.io/getting-started/launch/)).

**Определение Dockerfile.** Поведение зависит от того, что ещё обнаружено ([Create an app with Fly Launch](https://docs.fly.io/launch/create/)):

- Нет Dockerfile + поддерживаемый фреймворк → генерирует Dockerfile (для JS-фреймворков через `@flydotio/dockerfile`) и обычно `.dockerignore`.
- Есть Dockerfile + сканер Rails/Phoenix/JS-framework/Laravel → сканер настраивает приложение, но сохраняет ваш Dockerfile.
- Есть Dockerfile + всё остальное → берёт управление «Dockerfile scanner»: минимальная конфигурация, Dockerfile используется как есть, блокирует другие сканеры.
- Документация явно советует: для скриптов и coding-агентов сначала запускать `fly launch`, а затем править сгенерированный Dockerfile — написание своего Dockerfile с нуля заранее может помешать launch сгенерировать подходящий под фреймворк. (Для нашего случая Dockerfile уже есть в проекте; ожидаемый путь — Dockerfile scanner.)

**Интерактивные промпты.** Сводка launch показывает Organization (по умолчанию personal org), Name (из имени директории; должен быть глобально уникален — частые имена отклоняются), Region (ближайший к вам), Machine size и предложения Postgres/Redis, затем спрашивает «Do you want to tweak these settings before proceeding?», что открывает веб-страницу Fly Launch ([Create an app with Fly Launch](https://docs.fly.io/launch/create/)). CLI v0.5.1 подтверждает переключатели провижининга: `--db` (mpg / upg / true), `--no-db`, `--no-redis`, `--no-object-storage`, `--no-github-workflow` (`fly launch --help`). Точный текст промптов для пути с чистым Dockerfile в v0.5.1 не проверялся без запуска launch — считайте Django-пример из документации репрезентативным, а не буквальным.

**Неинтерактивные флаги** (`fly launch --help`, v0.5.1; документация команды: [fly launch](https://docs.fly.io/flyctl/cmd/fly_launch/)): `--name`, `-r/--region` (см. `fly platform regions`), `--org`, `-y/--yes` (принять все подтверждения), `--no-deploy` (создать и настроить, не деплоить), `--now` (деплоить без подтверждения), `--generate-name`, `--copy-config` (использовать существующий fly.toml без вопросов), `--dockerfile <path>`, `-i/--image <image>` (полностью пропустить сборку), `--internal-port`, `-e/--env NAME=VALUE`, `-v/--volume name:/path` с `--volume-initial-size`, `--vm-size` / `--vm-cpus` / `--vm-memory` / `--vm-cpu-kind`, `--auto-stop off|stop|suspend` (по умолчанию `stop`), `--ha` (по умолчанию true — создаёт запасные машины для доступности), `--no-public-ips`, `--dockerignore-from-gitignore`, `--path` (куда записывается fly.toml), `--remote-only`/`--local-only`/`--depot` для сборок.

**Генерируемые файлы.** `fly.toml` в корне проекта (или `--path`) и обычно `.dockerignore` (опционально производный от `.gitignore` через `--dockerignore-from-gitignore`); Dockerfile — только когда его генерирует сканер ([Create an app with Fly Launch](https://docs.fly.io/launch/create/)). `--json`/`--yaml` выдают конфигурацию в других форматах ([App configuration](https://docs.fly.io/reference/configuration/)).

**Выводы для скилла:** Предпочитать полностью неинтерактивный запуск: `fly launch --name <unique> --region <r> --no-deploy --yes` (с `--dockerfile <path>`, если Dockerfile не `./Dockerfile`), затем правка `fly.toml`, затем `fly deploy`. Для этого проекта добавить `--no-db --no-redis --no-object-storage` для подавления предложений ресурсов и рассмотреть `--ha=false` для одномашинного SQLite-приложения. Проверять уникальность имени приложения — формировать из имени репозитория + случайный суффикс, а не только из имени директории. Не позволять launch заменить руками написанный Dockerfile проекта; если сканер это предлагает — отказаться (неинтерактивный режим сохраняет его, если не передан `--yes` для Django/RedwoodJS/старых Laravel — не наш путь, но будьте осторожны, комбинируя `--yes` с обнаруженными фреймворками).

## 3. Справочник `fly.toml` (схема Machines / Apps V2)

Источник всего раздела: [App configuration (fly.toml)](https://docs.fly.io/reference/configuration/).

- `app = "name"` — первый ключ; также определяет hostname по умолчанию `<app>.fly.dev`. flyctl подхватывает приложение из `fly.toml` в текущей директории; переопределение: `-a` (приложение) или `-c` (путь к конфигу).
- `primary_region = "ord"` — где `fly deploy` создаёт новые Machines; также устанавливает env `PRIMARY_REGION` внутри Machines (переопределяет `[env]`).
- `[build]` — `dockerfile = "Dockerfile.test"` (относительный путь или URL; по умолчанию `Dockerfile` в корне проекта; НЕ меняет build context — контекст остаётся корнем проекта; не исключайте Dockerfile через `.dockerignore`), `image = "repo:tag"` (деплой готового образа), `builder`/`buildpacks` (buildpacks — документация называет их медленными и хрупкими, избегать), `build-target`, `ignorefile`, `[build.args]` (только на этапе сборки, не в рантайме).
- `[http_service]` — простой сервис для HTTP/HTTPS-приложений; заменяет `[[services]]`, когда нужны только порты 80/443. Ключи: `internal_port` (по умолчанию 8080; должен совпадать с портом, который слушает приложение), `force_https` (301-редирект HTTP→HTTPS), `auto_stop_machines = "off"|"stop"|"suspend"` (по умолчанию `"off"`, если не задано; но `fly launch` записывает настройки scale-to-zero), `auto_start_machines` (по умолчанию `true`), `min_machines_running` (по умолчанию `0`; только в primary-регионе), `[http_service.concurrency]` (`type = "requests"` рекомендуется для HTTP-приложений; `soft_limit` по умолчанию 20, `hard_limit` опционально), `[http_service.tls_options]`, `[http_service.http_options]` (idle_timeout, заголовки ответа, h2_backend).
- `[[http_service.checks]]` — HTTP health checks: `grace_period` (дать приложению время на старт), `interval`, `timeout`, `method`, `path`, `protocol`; ожидают 2xx, НЕ следуют редиректам (корень, редиректящий из-за `force_https`, провалит `http`-проверку — добавьте заголовок `X-Forwarded-Proto = "https"` или используйте выделенный эндпоинт с 200). Секция `[checks]` верхнего уровня существует для приложений без публичных сервисов.
- `[env]` — несекретные runtime-переменные окружения; только строковые значения; имена не должны начинаться с `FLY_`; секреты переопределяют одноимённые env.
- `[[vm]]` — вычисления: `size` (например, `shared-cpu-1x`; имена пресетов из `fly platform vm-sizes`), `memory` («1gb» или целое в MB), `cpus` (1/2/4/8/16), `cpu_kind = "shared"|"performance"`. У `size` самый низкий приоритет среди ключей. Размер Machine по умолчанию — `shared-cpu-1x`, но не применяется, если отсутствует в fly.toml; изменения `fly scale vm` сбрасываются следующим `fly deploy`, если `[[vm]]` задан. Возможны секции `[[vm]]` по process-группам.
- `[mounts]` — `source` (имя volume; volume с таким именем должен существовать в каком-то регионе для деплоя), `destination` (путь монтирования; не может быть `/`), опционально `processes`, `initial_size`, `snapshot_retention` (дни, по умолчанию 5, диапазон 1–60), `scheduled_snapshots` (по умолчанию true), `auto_extend_size_threshold`/`_increment`/`_limit` для автоматического роста volume.
- `[deploy]` — `strategy` (`rolling` по умолчанию / `immediate` / `canary` / `bluegreen`; canary и bluegreen НЕ разрешены для Machines с присоединёнными volumes), `max_unavailable` (rolling; по умолчанию 0.33), `release_command` (разовая предрелизная задача во временной Machine — без volumes, заменяет CMD, но не ENTRYPOINT, проваливает деплой при ненулевом коде выхода, таймаут по умолчанию 5 минут), `wait_timeout` (по умолчанию 5 минут ожидания состояния/здоровья на Machine).
- Опции верхнего уровня: `kill_signal` (по умолчанию SIGINT), `kill_timeout` (по умолчанию 5 с, максимум 300 с), `swap_size_mb`, `console_command`. Политика `[[restart]]` (по умолчанию `on-failure`), `[metrics]`, `[[statics]]` (отдача файлов из образа Machine через Fly Proxy — заметьте: требует запущенной Machine, без кастомных заголовков), `[[files]]` (размещение файлов/секретов-как-файлов при загрузке).

**Устаревшее / legacy.** Старая платформа «Apps V1» на Nomad ушла; текущая конфигурация — Machines (V2): Machines, созданные `fly deploy`, несут метаданные `"fly_platform_version": "v2"` ([Deploy an app](https://docs.fly.io/launch/deploy/)). `[[services]]` НЕ устарела — это по-прежнему полнофункциональная форма; `[http_service]` — рекомендуемая более простая альтернатива для чистых HTTP/HTTPS-приложений ([App configuration](https://docs.fly.io/reference/configuration/)). Старые туториалы с `[[services]]` и явными `[[services.ports]]` всё ещё валидны, просто многословнее.

**Выводы для скилла:** Генерировать/проверять fly.toml с: `app`, `primary_region`, `[http_service]` с `internal_port`, равным порту прослушивания приложения, `force_https = true`, явными настройками autostop, `[[vm]] size = "shared-cpu-1x"` с `memory`, `[env]` для `PORT` (если дефолты контейнера отличаются) и `DATABASE_PATH`, указывающим на mount volume, `[[http_service.checks]]` против health-эндпоинта, возвращающего 200 без редиректов, и `[mounts]` для SQLite volume. Валидировать через `fly config validate` (по [Troubleshoot your deployment](https://docs.fly.io/getting-started/troubleshooting/)).

## 4. Поведение Machines

- **Autostop/autostart.** Fly Proxy останавливает/усыпляет (suspend) Machines, когда у приложения избыточная ёмкость (одна Machine без трафика останавливается/усыпляется) и запускает её при поступлении запроса; цикл остановки выполняется раз в несколько минут ([Autostop/autostart Machines](https://docs.fly.io/launch/autostop-autostart/), [App configuration](https://docs.fly.io/reference/configuration/)). `fly launch` по умолчанию записывает настройки scale-to-zero (`auto_stop_machines = "stop"`, `auto_start_machines = true`, `min_machines_running = 0`) ([Autostop/autostart Machines](https://docs.fly.io/launch/autostop-autostart/)). Холодный старт из `stopped` ≈ 2 с и более; возобновление из `suspended` — несколько сотен миллисекунд, но имеет проблемы со сдвигом часов (clock skew), которые могут сломать валидацию JWT, cron, TTL кешей и проверки TLS сразу после возобновления ([Troubleshoot — Suspend vs stop](https://docs.fly.io/getting-started/troubleshooting/)). Документация рекомендует включать или выключать auto_stop и auto_start вместе. Autostop никогда не создаёт и не уничтожает Machines — максимум работающих = число созданных вами Machines.
- **Состояния Machine.** Персистентные: `created`, `started`, `stopped`, `suspended`, `failed`. Переходные: `creating`, `starting`, `stopping`, `restarting`, `suspending`, `destroying`, `launch_failed`, `updating`, `replacing`. Терминальные: `destroyed`, `replaced` (старые версии), `migrated` ([Machine states and lifecycle](https://docs.fly.io/machines/machine-states/)). Пороги «застревания»: >5 минут в `starting`/`stopping`/`restarting`/`destroying`, >10 минут в `updating`.
- **Регионы.** `fly platform regions` перечисляет регионы (проверено в help; документация: [Regions](https://docs.fly.io/reference/regions/)) — 17 регионов, трёхбуквенные коды (ams, iad, fra, ...). Machines и volumes привязаны к своему региону; env `FLY_REGION` устанавливается внутри каждой Machine.
- **Наблюдение.** `fly status` показывает статус приложения, Machines и регионы; `--all` показывает также завершённые инстансы; `--watch` обновляет (`fly status --help`). `fly machines list` (алиас `fly machine list`) перечисляет Machines с состоянием, регионом, образом, присоединённым volume. `fly logs` стримит логи; `-n/--no-tail` для снапшота, `-m <machine>` / `-r <region>` — фильтры, `-j` — JSON (`fly logs --help`). `fly ssh console` открывает шелл в запущенной Machine; `-C "<cmd>"` выполняет команду неинтерактивно, `--machine <id>` или `-s` выбирает Machine (`fly ssh console --help`; документация использует `fly ssh console -s -C df` для проверки монтирования volume в [Add volume storage](https://docs.fly.io/launch/volume-storage/)). `fly console` запускает настроенную `console_command` в новой одноразовой Machine.

**Выводы для скилла:** После деплоя проверять через `fly status` (Machines в `started`), `fly logs -n` (чистая загрузка, правильный порт) и HTTP-пробу. Инструктировать приложение слушать `0.0.0.0`. Для одномашинного SQLite-приложения предпочитать `auto_stop_machines = "stop"` (не `suspend`), если приложение валидирует временные метки при загрузке, либо держать `min_machines_running = 1`, чтобы вообще избежать холодных стартов.

## 5. Жизненный цикл деплоя

**Поток.** `fly deploy` собирает/получает образ, пушит его в реестр Fly, затем обновляет или создаёт Machines согласно `fly.toml` ([Deploy an app](https://docs.fly.io/launch/deploy/)). Приоритет выбора образа: (1) флаг `--image` или `[build].image`, (2) секция `[build]` (dockerfile/builder), (3) флаг `--dockerfile`, (4) `Dockerfile`/`dockerfile` в текущей директории ([Deploy an app](https://docs.fly.io/launch/deploy/)). Первый деплой создаёт Machines (две по умолчанию для избыточности, когда настроены сервисы, если только volumes не диктуют иное — см. [Redundancy by default on first deploy](https://docs.fly.io/apps/app-availability/#redundancy-by-default-on-first-deploy)); если у приложения есть подходящий HTTP-сервис и ещё нет публичных IP, деплой автоматически выделяет выделенный Anycast IPv6 и shared IPv4. Smoke checks наблюдают каждую Machine ~10 с после старта; повторяющиеся падения останавливают деплой. Опциональный `[deploy] release_command` выполняет разовые задачи (миграции) во временной Machine без volumes перед релизом.

**Флаги** (`fly deploy --help`, v0.5.1; [документация команды fly deploy](https://docs.fly.io/flyctl/cmd/fly_deploy/)): `--build-only`, `-i/--image`, `--push`, `--strategy rolling|immediate|canary|bluegreen` (по умолчанию rolling), `--ha` (по умолчанию true), `--vm-size` / `--vm-memory` / `--vm-cpus` / `--vm-cpu-kind`, `--wait-timeout` (по умолчанию 5м), `--max-unavailable` (по умолчанию 0.33), `-e/--env`, `--build-arg`, `--build-secret`, `--build-target`, `--no-cache`, `--local-only` / `--remote-only` (по умолчанию) / `--depot`, `--detach`, `--regions` / `--only-machines` / `--exclude-regions`, `--skip-release-command`, `--release-command-timeout`, `--image-label`, `-a` / `-c`, `-y` отсутствует у deploy (для подтверждений используйте launch; у deploy есть `--now`).

**Health checks.** `[http_service.checks]` / `[[services.http_checks]]` / `[[services.tcp_checks]]` выполняются постоянно и регулируют трафик; bluegreen требует хотя бы одну health-проверку ([App configuration](https://docs.fly.io/reference/configuration/)). `fly checks list` показывает текущие результаты ([Troubleshoot](https://docs.fly.io/getting-started/troubleshooting/)).

**Откат.** Команды `rollback` нет: откат — это передеплой предыдущего образа. `fly releases --image` перечисляет прошлые релизы со ссылками на образы; `fly deploy --image registry.fly.io/<app>:<tag>` передеплоит этот образ; используйте `--image-label` при деплое для человекочитаемых меток; заметьте: откаты не возвращают fly.toml/секреты и не откатывают миграции БД, а старые образы могут быть вычищены из реестра ([Roll back a deploy](https://docs.fly.io/blueprints/rollback-guide/)).

**Выводы для скилла:** При первом деплое приложения с volume помнить, что canary/bluegreen недоступны (rolling — дефолт и подходит). Всегда настраивать HTTP health check, чтобы деплои проверяли готовность. При сбое: читать `fly logs`, затем `fly releases --image` + `fly deploy --image <previous>` для отката, предупреждая, что миграции БД не откатываются. Использовать `--wait-timeout` для медленных загрузок вместо циклов повторов.

## 6. Сеть

Источник: [Public Network Services](https://docs.fly.io/networking/services/), [App configuration](https://docs.fly.io/reference/configuration/).

- **Anycast IP.** Приложения с публичным HTTP-сервисом в fly.toml (включая `[http_service]`) автоматически получают выделенный Anycast IPv6 и shared Anycast IPv4 при первом деплое — `fly ips allocate-v4/v6` НЕ нужен для приложений, созданных через `fly launch`/`fly deploy` (только для приложений, созданных через `fly machine run` / Machines API). IPv6 и shared IPv4 бесплатны; выделенный IPv4 (`fly ips allocate-v4` без `--shared`) оплачивается помесячно и нужен только для не-HTTP протоколов без TLS, UDP или самостоятельно терминируемого TLS. Egress IP — отдельная история (`fly machine egress-ip` — legacy / `fly ips allocate-egress` — на приложение) и не относится ко входящему трафику.
- **Маппинг портов.** Fly Proxy слушает 80 (http-обработчик) и 443 (tls + http-обработчики) и пересылает на `internal_port` (по умолчанию 8080) на Machine по приватной сети. Приложение должно слушать `0.0.0.0:<internal_port>`; привязка к `localhost`/`127.0.0.1` и несовпадение портов — классическая ошибка «not listening on the expected address» ([Troubleshoot](https://docs.fly.io/getting-started/troubleshooting/)). Собственный пример документации для нашего стека: `fastify.listen({ port: 8080, host: '0.0.0.0' })`.
- **Терминация TLS и force_https.** Обработчик `tls` терминирует TLS на границе сети с сертификатами, управляемыми Fly (автоматически для `<app>.fly.dev`); трафик к Machine идёт открытым текстом. `force_https = true` заставляет HTTP-запросы возвращать 301-редирект; валидно только на http-обработчиках.
- **Заголовки.** Http-обработчик добавляет `Fly-Client-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-SSL`, `Fly-Region` и др.; приложения за `force_https` должны доверять `X-Forwarded-Proto` при генерации редиректов/URL.
- Default-deny: ничего не открыто наружу, пока не настроен сервис.

**Выводы для скилла:** Устанавливать `internal_port` в соответствии с портом прослушивания контейнера либо стандартизировать контейнер на `PORT=8080` и оставить дефолт fly.toml. Поскольку приложение читает env `PORT`, скилл должен либо задать `[env] PORT`, либо передать `--internal-port $(PORT)` — оба значения обязаны совпадать. Включать `force_https = true` и убедиться, что Fastify работает с `trustProxy`, если он смотрит на протокол/IP клиента (документация не покрывает Fastify trustProxy — это знание со стороны приложения, не из документации Fly).

## 7. Volumes для персистентности SQLite

Источники: [Fly Volumes overview](https://docs.fly.io/volumes/overview/), [Add volume storage to a Fly Launch app](https://docs.fly.io/launch/volume-storage/), [JavaScript: Volumes](https://docs.fly.io/js/the-basics/volumes/), [App configuration — mounts](https://docs.fly.io/reference/configuration/).

- Корневая ФС Machine эфемерна; данные SQLite должны жить на volume. Документация подтверждает SQLite-на-volume как стандартный паттерн для JS-приложений (задайте `DATABASE_URL`/путь на mount) и Rails/Laravel-эквиваленты.
- **Создание:** `fly volumes create <name> -r <region> -s <GB> [-n count]` — размер по умолчанию 1 ГБ, максимум 500 ГБ, шифрование по умолчанию включено (`--no-encryption` для отказа), `--require-unique-zone` по умолчанию true, `--snapshot-retention` по умолчанию 5 дней (проверено через `fly volumes create --help`, v0.5.1).
- **Присоединение:** `[mounts] source = "<name>", destination = "/data"` в fly.toml. Один volume ↔ одна Machine: volume присоединяется ровно к одной Machine, Machine монтирует один volume на `[mounts]`; нужно столько одноимённых volumes, сколько Machines. Volumes — это локальные NVMe на том же физическом хосте, привязаны к одному региону, не сетевое хранилище, не разделяются между приложениями и не реплицируются — репликация задача приложения (LiteFS или бэкапы в стиле Litestream).
- При первом деплое с `[mounts]` flyctl создаёт volume, если нет свободного; `initial_size` в `[mounts]` (или `--volume-initial-size`) управляет размером автоматически создаваемого. Volumes НЕ доступны на этапе сборки и в Machines для `release_command`.
- **Предупреждение об избыточности (документация, по смыслу):** всегда выделяйте минимум два volume на приложение — одна Machine+volume означает простой при отказе хоста, при каждом деплое и потерю данных при отказе диска. Для SQLite-приложения с одним писателем документация допускает исключение — одна Machine с собственным планом бэкапов; документация указывает на LiteFS для реплицируемого SQLite.
- **Снапшоты/бэкапы.** Ежедневные блочные снапшоты, хранятся 5 дней по умолчанию (настраивается 1–60 через `[mounts] snapshot_retention`); снапшоты «не должны быть вашим основным методом бэкапа». `fly volumes list`, `fly volumes snapshots list <vol-id>` (по документу troubleshooting), восстановление через `fly volumes create <name> --snapshot-id <id> -r <region>` ([Troubleshoot — Volumes and disk errors](https://docs.fly.io/getting-started/troubleshooting/)), форк через `fly volumes fork` для копий ([Fly Volumes overview](https://docs.fly.io/volumes/overview/)).
- Биллинг: volumes оплачиваются за полный выделенный размер, даже когда Machine остановлена — на простаивающем приложении volume может стоить больше, чем вычисления ([Autostop/autostart Machines](https://docs.fly.io/launch/autostop-autostart/)).

**Выводы для скилла:** Скилл должен: выбрать mount (например, `/data`), задать `DATABASE_PATH=/data/...` в `[env]`, создать один volume в primary-регионе до/при первом деплое, держать приложение ровно на одной Machine на volume (один писатель; семантика `fly scale count 1`), никогда не запускать две Machines против одного volume, отключать `--ha` при launch (две Machines ⇒ два volumes ⇒ split-brain SQLite) и прямо говорить, что ежедневные снапшоты — не стратегия бэкапа: внеполосный бэкап (например, периодическое копирование в object storage) — на пользователе. Volumes нельзя уменьшить, только расширить.

## 8. Секреты и env

Источник: [Secrets and Fly Apps](https://docs.fly.io/apps/secrets/), [App configuration — env](https://docs.fly.io/reference/configuration/).

- `[env]` в fly.toml: несекретные значения открытым текстом, в закоммиченном конфиге; только строки; имена не должны начинаться с `FLY_`.
- `fly secrets set NAME=VALUE [...]`: зашифрованное хранилище, инжектируется как переменные окружения при загрузке Machine на каждой Machine приложения. Установка секретов триггерит деплой/перезапуск Machines (сброс эфемерной корневой ФС) — используйте `--stage` для откладывания до следующего деплоя или `fly secrets deploy`. Принимает значения из stdin. `fly secrets list` показывает только имена + дайджесты; значения никогда не читаются. `fly secrets unset` удаляет. Секреты переопределяют одноимённые переменные `[env]`. Секреты НЕ доступны на этапе Docker-сборки — используйте `[build.args]` / `--build-secret` для этого.
- Секреты-как-файлы: `[[files]] guest_path=..., secret_name=...` с base64-закодированными значениями секретов.

**Выводы для скилла:** Класть `PORT` и `DATABASE_PATH` в `[env]` (они не секретные), чтобы конфигурация была самодостаточной и ревьюируемой; `fly secrets set` оставить для учётных данных (для базового SQLite-деплоя не нужны). Предупреждать, что каждый `fly secrets set` перезапускает Machines — группировать секреты до деплоя или использовать `--stage`.

## 9. Траблшутинг для агентов

Источник: [Troubleshoot your deployment](https://docs.fly.io/getting-started/troubleshooting/), если не указано иное; команды проверены по `--help` v0.5.1, где отмечено.

- Первые шаги: обновить flyctl (документация говорит `fly version update`; в v0.5.1 подкоманда — `fly version upgrade` — проверено `fly version --help`), `fly doctor` (проверяет WireGuard, IP, Docker; `fly doctor --help` проверено), `fly config validate` (`--help` проверено), `fly logs` во втором терминале, `LOG_LEVEL=debug fly deploy`.
- 502: приложение упало или неверный адрес/порт прослушивания → `fly logs`. 503: нет здоровых Machines → `fly status`, `fly checks list` (`--help` проверено; ошибки health-check вроде «connection refused» не появляются в логах приложения).
- «App is not listening on the expected address»: слушать `0.0.0.0` и совпасть с `internal_port`.
- Health checks: задавать `grace_period` (10–30 с для медленно стартующих), использовать выделенный эндпоинт, всегда возвращающий 200, помнить, что проверки не следуют редиректам.
- Ошибки сборки: удалённые сборки используют Depot; если сборка висит на «Waiting for depot builder», повторить с `fly deploy --depot=false` (legacy remote builder) или `fly deploy --local-only` (нужен локальный Docker). `exit code: 1` в Dockerfile — проблема сборки приложения, воспроизводится через `docker build .`. Лимит образа: 8 ГБ rootfs; используйте multi-stage сборки и `.dockerignore`. Registry 401 при пуше → перелогиниться или проверить status.flyio.net. `fly deploy --help` подтверждает `--depot` (по умолчанию «auto»), `--local-only`, `--remote-only`, `--no-cache`.
- Застрявшая Machine: `fly machine restart <id>`, затем `fly machine update <id> --yes --metadata foo=bar`, затем `fly machine destroy --force <id>` + `fly scale count <n>`.
- Machine останавливается сразу после старта: процесс завершается — убедитесь в явном `CMD` в Dockerfile, проверьте `docker run`, смотрите `fly logs`.
- `fly ssh console` в Machine (`-C "cmd"` для разовых команд); ssh/приватный доступ работает через WireGuard (`fly wireguard --help` проверено: create/list/remove/reset peers; `fly doctor` покрывает его).
- Готовые образы / реестр: `fly auth docker` добавляет учётные данные registry.fly.io в конфиг Docker-демона (`fly auth docker --help` проверено); затем `docker build -t registry.fly.io/<app>:<tag> . && docker push ...` и `fly deploy --image registry.fly.io/<app>:<tag>`; существование проверяется через `docker manifest inspect` ([Using the Fly Docker Registry](https://docs.fly.io/blueprints/using-the-fly-docker-registry/)). API перечисления тегов нет — задеплоенные образы видны через `fly releases --image` (`fly releases --help` проверено).
- Статус платформы: https://status.flyio.net.

**Выводы для скилла:** Дать агенту детерминированную лестницу сбоев: `fly status --all` → `fly logs -n` → `fly checks list` → `fly config validate` → `fly doctor` → локальная пересборка (`docker build .`) → `--depot=false`/`--local-only` → откат через `fly releases --image`. Запретить слепые циклы повторов и деструктивную хирургию Machines, если пользователь её не просил.

## 10. Параметры, влияющие на цену

Документация намеренно держит цены на одной странице: [Pricing](https://docs.fly.io/about/pricing/) (пресеты вычислений, правила для остановленных Machines, Anycast IP). Что важно для скилла, по документации:

- Размеры Machines — пресеты (`shared-cpu-1x` … `performance-16x`); перечислить: `fly platform vm-sizes` ([App configuration — vm](https://docs.fly.io/reference/configuration/)).
- Остановленные/усыплённые Machines не тарифицируются за CPU/RAM — только rootfs ($0.15/ГБ за 30 дней в примере документации); volumes тарифицируются за полный выделенный размер независимо от состояния ([Autostop/autostart Machines](https://docs.fly.io/launch/autostop-autostart/)).
- IPv6 и shared IPv4 Anycast бесплатны; выделенный IPv4 оплачивается помесячно ([Public Network Services](https://docs.fly.io/networking/services/)).

**Выводы для скилла:** По умолчанию `shared-cpu-1x`, настройки scale-to-zero и shared IPv4 (автоматический дефолт); явно показывать, что volume имеет постоянную месячную стоимость даже при простое; ссылаться на страницу цен вместо цитирования цифр (они меняются).
