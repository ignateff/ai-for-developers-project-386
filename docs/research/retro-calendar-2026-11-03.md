Ключевые границы выбранного пакета:

- Деплой запускается явно, без автоматического CD и Fly-секретов в CI. Команда работает только из уже выбранного чистого `main`, сама не переключает ветки/worktree; выполняет свежий fetch, fast-forward-only обновление и проверку точного совпадения ревизий. Существующие требования безопасного контекста, происхождения образа, повторного Git-gate и проверки публичной версии сохраняются. Настоящий деплой — только по отдельному запросу.
- Docker smoke входит в полный `mise run check` локально и в CI согласно #18. Недоступный Docker — явная ошибка, не пропуск. Быстрые hooks остаются без Docker. Smoke проверяет текущую рабочую копию, включая незакоммиченные изменения; deploy-gate к локальным проверкам не применяется.
- Для smoke и деплоя выбрана платформа `linux/amd64`; на Apple Silicon принимаем более медленную эмуляцию. Реальный контейнер запускается обычным CMD с `PORT=8080`; проверяются главная, health и frontend-версия в браузере. Полный сценарий записи остаётся в существующих E2E.
- Тесты deploy-команды используют подставные Git/Fly/Docker-интерфейсы без настоящих credentials; smoke использует настоящий контейнер с изолированными данными. Документационные изменения проверяются по ссылкам и первичным источникам.
- Индекс опирается на существующие доказательства и решения, без архива всех разговоров и повторения исследований. Исправления документации сохраняют дату и контекст исторических наблюдений. Сторонние skills Matt Pocock и глобальные настройки не меняются.

Пакет не блокирует отправку наставнику без выявленного нарушения критериев приёмки. Следующий шаг — `/to-spec`, затем согласование `/to-tickets`; это запись решений, а не начало реализации.

## Главное наблюдение

Многие повторные затруднения уже устранены. Следующий полезный шаг — превратить оставшиеся механические процедуры в проверяемые инструменты, а не расширять `AGENTS.md` новыми напоминаниями. Там, где требуется человеческое решение, полезнее короткий указатель на существующее доказательство или принятое решение.

## Кандидаты по приоритету

### 1. P1 — Автоматизировать безопасный деплой

**Наблюдение.** В нескольких сессиях повторялись подготовка контекста, сборка, публикация, выяснение текущего образа и проверка версии. В сессии «Отображение версии приложения в консоли браузера» агент прервал публикацию собственным лимитом инструмента в 120 секунд. В последней deploy-сессии понадобились новые временные Python-процедуры для Git-gate, снимка исходников и связи SHA с digest.

**Текущее состояние.** [Skill Fly](../../.agents/skills/fly-deploy/SKILL.md) уже описывает долгие операции, безопасное восстановление и main-only gate. В [его справочнике](../../.agents/skills/fly-deploy/reference/fly-io.md#проектная-deploy-команда) есть требования к будущей deploy-команде. Однако `deploy:fly` отсутствует в [mise](../../mise.toml) и [package scripts](../../package.json); [build-docker.mjs](../../scripts/build-docker.mjs) только собирает образ.

**Предложение.** Согласовать и реализовать `mise run deploy:fly`: чистый синхронизированный `main`, безопасный контекст, build-time revision, связь проверенного образа с registry digest, повторный gate перед публикацией и rollout, достаточный бюджет выполнения, сверка машины и публичной версии. Не выполнять автоматический повтор мутации с неизвестным исходом. Подготовку, аргументы, отказ на неподходящем Git-состоянии и ошибки CLI проверять тестами без live credentials.

**Ограничение.** Автоматизация уменьшит вариативность действий агента, но не устранит сетевые EOF провайдера. Точная первопричина прежних сетевых ошибок не доказана.

### 2. P1 — Добавить независимую Docker-проверку в CI

**Наблюдение.** Аудит приёмки обнаружил в зелёном `hexlet-check` сообщение `Tests will run during review step`; это не результат фактического Docker smoke. Корректность контейнера пришлось подтверждать отдельно. Подробности и ссылки на прогоны сохранены в [отчёте приёмки](mentor-readiness-2026-11-02.md#наблюдения-аудита-запуск-и-проверки).

**Текущее состояние.** [Собственный CI](../../.github/workflows/ci.yml) запускает полный `mise run check`, но не собирает и не запускает production-контейнер. [build-docker.test.ts](../../scripts/build-docker.test.ts) проверяет аргументы команды и код завершения с подставным Docker, а не реальный runtime.

**Предложение.** Добавить mise-задачу и job в существующий CI: собрать образ, запустить обычный CMD с `PORT=8080` и изолированной БД, дождаться готовности с конечным бюджетом, проверить `/`, `/api/health` и frontend build identity; при ошибке сохранить диагностику и убрать только созданные проверкой ресурсы. Генерируемый workflow Хекслета оставить без изменений.

**Отдельный кандидат.** Измеренный в последнем деплое linux/amd64-образ занимал около 1,16 ГБ, из них примерно 925 МБ — слой установки зависимостей. Можно отдельно оценить multi-stage runtime без инструментов сборки и dev dependencies. Проверить нативный `better-sqlite3`, миграции и frontend-артефакты. Размер образа — фактор объёма публикации, не доказательство причины EOF; порог размера заранее не согласован.

### 3. P2 — Сделать доказательства приёмки и решения находимыми

**Наблюдение.** Первоначальный аудит пропустил уже опубликованный [red→green-эксперимент в #21](https://github.com/ignateff/ai-for-developers-project-386/issues/21#issuecomment-6558898063) и предложил повторить его. Пользователю также пришлось напоминать о карте решений и результате исследований серверных генераторов.

**Предложение.** Расширить существующую [трассировку](../agents/implementation-traceability.md) компактными указателями вида «критерий → доказательство → принятое решение → ограничения». Результат экспериментов генерации оформить как принятое решение со ссылками на #43/#44 и исследование, а не как ещё одну рекомендацию повторить эксперимент. Не приписывать прошлым действиям отсутствующие доказательства и не переписывать опубликованную Git-историю.

**Граница.** Индекс — навигация, не новый обязательный архив всех команд и разговоров. Отсутствие найденного лога не доказывает, что действие никогда не выполнялось. Исторический [обзор генераторов](fastify-server-generation.md) не является ADR и не описывает все последующие эксперименты.

### 4. P2 — Отделить актуальные инструкции от исторических наблюдений

**Наблюдение.** На проверенном снимке есть три противоречия:

- [ADR 0001, «Текущее состояние»](../adr/0001-technology-stack.md#текущее-состояние) сообщает, что SQLite, Docker и Playwright ещё не подключены.
- [Design README](../design/README.md#как-читать-макет) предлагает читать `.pen` как JSON и получать frame IDs из сырого файла; текущие инструкции Pencil требуют обращаться к `.pen` только через MCP. Ранее относительный `filePath` также привёл к чтению другого активного документа; требование абсолютного пути уже добавлено.
- [Предыдущее ретро](retro-parallel-worktrees.md) описывает полный `mise run check` в hooks, тогда как [текущие hooks](../../hk.pkl) выполняют `check:quick`.

**Предложение.** Исторические результаты явно привязать к дате или коммиту; рабочие инструкции направлять на актуальную документацию. Для дизайна оставить безопасное чтение через MCP и существующий HTML fallback, не предлагая обход ограничений инструмента. Не превращать каждый старый исследовательский снимок в постоянно обновляемое описание всего проекта.

### 5. P2 — Устранить конфликт глобального `commit-msg` с проектом

**Наблюдение.** В первой сессии пользователь попросил не применять `commit-msg`. Проверенный глобальный skill всё ещё требует Jira-префикс `[IVINET-XXXX]`, тогда как календарь использует Conventional Commits и ссылки на GitHub Issues.

**Предложение.** Отдельно согласовать ограничение Jira-specific навыка соответствующими рабочими проектами, сохранив его поведение там. Для календаря рассмотреть детерминированную проверку Conventional Commits и issue-ссылок новых implementation-коммитов через hook и PR-проверку. Политику для merge/release-коммитов, проверяемого диапазона и английского текста уточнить до реализации; синтаксическая проверка не докажет качество или язык произвольного описания.

**Граница.** Не менять глобальные настройки без отдельного согласия и не переписывать старые коммиты. Сторонние skills Matt Pocock сохранять как поставлены.

### 6. P2 — Завершить существующую #56 о доказательности теста гонки

**Наблюдение.** Итоговое ревью #51 установило: `route.fulfill()` и получение HTTP-ответа не доказывают, что приложение обработало результат. Поэтому проверка disabled-состояния могла пройти до применения устаревшего ответа. Последующая попытка через QueryCache также не дала надёжного наблюдаемого сигнала для отброшенного результата.

**Предложение.** Продолжить [#56](https://github.com/ignateff/ai-for-developers-project-386/issues/56): выбрать согласованную наблюдаемую границу обработки или отбрасывания результата, сделать старые и новые данные различимыми, удерживать свежий ответ и доказать red→green на соответствующей регрессии. Сохранить пользовательские проверки, не добавлять тестовые индикаторы в UI и не усложнять архитектуру исключительно ради теста.

**Граница.** Это известное ограничение покрытия, не подтверждённая ошибка записи. Дубликат Issue не нужен. #42 отдельно отслеживает недоказанную причину исторического CI-сбоя и не заменяет #56.

### 7. P3 — Проверить доступность поисковой интеграции

**Наблюдение.** В выгруженных OpenCode-сессиях 15 из 31 вызова `websearch` завершились HTTP 403. Разные агенты повторно обнаруживали ограничение и переходили к прямым первичным источникам. Это историческая статистика, не результат новой проверки поисковой интеграции.

**Предложение.** Отдельно диагностировать доступность и авторизацию выбранной интеграции без раскрытия credentials. Пока она недоступна, использовать официальные индексы документации, GitHub и npm напрямую, отмечая неполноту обзора. Не выводить причину отказа или отсутствие подходящего инструмента только из HTTP 403.

## Как вернуться к отчёту

Начать с обзорной #73, комментария согласования и актуального состояния выбранного направления. Объём ближайшего пакета и тестовые границы согласованы выше; для его подготовки использовать `/to-spec`, затем согласовать `/to-tickets`. Если обстоятельства изменились, уточнить затронутые решения через `/grill-with-docs`. #56 не входит в пакет; при отдельном возвращении к гонке использовать эту Issue, а не создавать дубликат.

В обзорной Issue выбранные, но ещё не реализованные направления оставлять незавершёнными. Отложенные и исключённые направления отмечать разрешёнными по объёму с явной причиной, а не как исправленные. Сохранение отчёта и согласование пакета сами по себе не закрывают обзорную Issue.
