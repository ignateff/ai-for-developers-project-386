# GitHub-агент OpenCode

> **Черновик, не включать.** Все четыре job принудительно отключены через `if: false && ...`. Независимое ревью выявило блокеры: интерактивная модель получает App token и может выполнить инструкции из недоверенного issue/PR; запрет push в `main` обходим refspec; формат вывода CLI не подтверждён для парсера triage. До включения нужно отделить анализ от контролируемых мутаций, исключить прямой доступ модели к write token, обеспечить проверяемый запрет push в main, подтвердить извлечение финального ответа CLI и закрепить каждый сценарий тестами. Версия npm-пакета зафиксирована, но транзитивные зависимости ещё не закреплены lockfile. Никакая переменная не включает эти jobs до исправления конфигурации.

## Конфигурация

На раннере используется OpenCode CLI `2.2.6`, standalone-режим и модель `anthropic/claude-sonnet-5-5`. Для неё владелец репозитория добавляет Actions secret `ANTHROPIC_API_KEY` через интерфейс GitHub или интерактивный `gh secret set ANTHROPIC_API_KEY`; значение не записывается в файлы, issue, PR или чат.

Workflows используют существующий GitHub App Release Please через `RELEASE_PLEASE_APP_ID` и `RELEASE_PLEASE_APP_PRIVATE_KEY`. Это осознанное переиспользование одного приложения, установленного только на репозиторий: App уже имеет Contents, Issues и Pull requests write. Комментарии и PR агента поэтому публикуются от App, а не от `GITHUB_TOKEN`. Для разделения identity можно создать отдельное App с теми же минимальными правами и заменить имена переменных во всех workflows.

После исправления блокеров и повторного ревью владелец отдельно решает, включать ли платные обращения. При использовании другого App нужно будет задать `OPENCODE_APP_BOT_LOGIN` — login его bot-пользователя; маркеры обычных пользователей не расходуют запуски.

До настройки секрета и включения переменной конфигурация не считается подтверждённым запуском модели. Прогоны появляются на вкладке [Actions](https://github.com/ignateff/ai-for-developers-project-386/actions); текст ответа сохраняется в artifact каждого запуска на 30 дней.

## Команды в комментариях

Команда начинается с mention `@opencode` и принимается только от `OWNER`, `MEMBER` или `COLLABORATOR`:

- `@opencode analyze <вопрос>` — разобрать issue или PR;
- `@opencode to-spec <уточнение>` — создать спецификацию и остановиться перед согласованием;
- `@opencode to-tickets` — после явного согласования спецификации создать связанные тикеты и остановиться перед их согласованием;
- `@opencode implement-spec` — после двух явных согласований выполнить реализацию, проверки и PR;
- `@opencode review <фокус>` — провести разбор по запросу;
- `@opencode fix <замечание>` — исправить замечание в текущей ветке PR.

Общий комментарий issue/PR и комментарий к строке diff обрабатывает `agent-interactive.yml`. Пустой mention и комментарии ботов игнорируются. При выполнении `implement-spec` агент обязан проверить два человеческих согласования; их отсутствие является причиной остановки, а не формальностью, которую можно обойти.

## Workflows

| Файл                    | Событие                                                                   | Результат                                                                           |
| ----------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `agent-interactive.yml` | созданный `issue_comment` или `pull_request_review_comment` с `@opencode` | ответ, артефакты issue/PR, изменения по доверенной команде                          |
| `agent-triage.yml`      | `issues: opened, reopened`                                                | одна каноническая метка и объяснение по критериям из `docs/agents/triage-labels.md` |
| `agent-review.yml`      | `pull_request: opened, synchronize, reopened, ready_for_review`           | read-only разбор по `REVIEW.md` с указанием точного head SHA                        |
| `agent-audit.yml`       | ежедневный `schedule` и ручной `workflow_dispatch` на `main`              | отчёт в artifact и отдельные issues только для новых находок                        |

Для ручной проверки регулярного сценария откройте **OpenCode scheduled audit → Run workflow**, оставьте `main`, при необходимости задайте дополнительный `prompt`. Ждать ночного запуска не нужно. Повторная публикация ищет стабильный маркер находки во всех открытых и закрытых issues, включая учебные задачи. Чистый аудит возвращает пустой список; учебная задача создаётся только по явному запросу в prompt и маркируется `learning:true`.

## Ограничения и безопасность

- `OPENCODE_MAX_RUNS_PER_PR` задаёт общий предел обращений к модели из review и interactive workflows; без переменной предел равен 3. Маркер учитывается до модели и остаётся даже при её ошибке. При исчерпании публикуется отказ с причиной, полным SHA и ссылкой на логи.
- Все agent jobs имеют `timeout-minutes` и concurrency. Новые bot-комментарии не вызывают интерактивный workflow; bot-issues не проходят автотриаж. PR агента получает авторевью наравне с PR человека, а лимит сдерживает цепочку synchronize.
- Fork PR исключаются до создания App token и до шага с ключом модели. Для `issue_comment` на PR сначала используется read-only `github.token` для проверки `head.repo.fork`; App и модель не вызываются для fork.
- Read-only triage/review/audit не получают `GH_TOKEN` во время работы модели. Их вывод валидируется, а изменения в GitHub выполняют отдельные детерминированные скрипты. У triage-агента дополнительно запрещены shell и web-инструменты: публичный текст issue остаётся данными и не даёт командного доступа к окружению с ключом модели.
- Отчёты находятся только в Actions artifacts и не копируются в рабочее дерево. Публичные сессии через `share` не используются: решение проекта — предоставлять доступный вывод через Actions и ссылки в комментариях, без публикации полного session transcript.
- `.agents/skills/` доступен runner как project compatibility source OpenCode. Добавлены `to-spec`, `to-tickets`, `implement-spec`; сохранённые материалы Мэтта Покока в `docs/agents/` и существующие навыки не заменяются. `AGENTS.md` остаётся источником актуальных install/check/test/deploy команд.

## Приёмочные доказательства, которые нельзя создать конфигурацией

После мержа владелец настраивает секрет, вызывает агента из issue и из двух видов PR-комментариев, вручную запускает аудит и проверяет App identity, artifact, issue-дедупликацию и отказ по лимиту. Выбранная доработка проходит реальные `to-spec` → согласование → `to-tickets` → согласование → `implement-spec`, браузерную проверку head SHA, независимое ревью и человеческий merge. Личную самооценку владелец пишет по этим фактическим прогонам; заранее заполненные успехи не публикуются.
